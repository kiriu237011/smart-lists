# Память проекта Smart Lists

> Живой снимок устойчивых знаний о проекте. Перед работой сверяй его с кодом и обновляй после существенных изменений.

**Последнее обновление:** 2026-08-26 (первый tenant policy-контур полностью

**Состояние:** активная разработка

## Назначение

Smart Lists — локализованное веб-приложение для личных и совместных списков. Пользователь организует списки по пространствам и группам, совместно редактирует записи и заметки, прикрепляет файлы и может запрашивать AI-инсайт.

Есть два режима данных:

- авторизованный — PostgreSQL, совместный доступ, Pusher, S3 и AI;
- гостевой — локальные данные браузера без шаринга, realtime, вложений и AI.

## Актуальный стек

- Next.js `16.3.1`, App Router, Server Components и Server Actions;
- React `19.2.8`, TypeScript strict, Tailwind CSS 4, Framer Motion и dnd-kit;
- Auth.js v5 с Google OAuth и Prisma Adapter;
- Prisma `7.9.1`, генератор `prisma-client`, `@prisma/adapter-pg` и PostgreSQL;
- runtime-пул `pg`: максимум 5 соединений на экземпляр, connect timeout 5 секунд, idle timeout 10 секунд;
- `next-intl`: `ru`, `vi`, `en`, `ja`; default locale — `en`;
- Pusher, приватный S3-бакет и внешний FastAPI-сервис AI-инсайтов;
- Zod, Pino, React Hot Toast, `next-themes` и `lucide-react`;
- Vitest — юнит-тесты чистых функций и схем валидации;
- React Markdown — только для ответов AI-инсайтов; остальной пользовательский текст разметку не разбирает;
- Vercel region — `sin1`.

Точные версии всегда смотри в `package.json` и `package-lock.json`.

## Модель данных и права доступа

### Доступ к PostgreSQL

- Runtime уже использует отдельную роль без DDL/ownership/BYPASSRLS. В Preview
  все восемь tenant-таблиц дополнительно ограничены RLS; в Production RLS и
  guard включены для `UserDailyUsage`, `List`, `Item`, `Space`, `ListGroup` и
  `_ListGroupMembers`. Только `ListShare` и `Attachment` пока сохраняют
  role-wide DML в рамках runtime ACL.
- `src/lib/scoped-db.ts` содержит foundation `withUserDb` и `withSpaceDb`:

- Вход выполняется через Google OAuth.
- Email должен существовать в `AllowedEmail`; whitelist управляется напрямую в БД.
- Сессии хранятся через Prisma Adapter; callback `session` добавляет `session.user.id`
  и там же сверяет email с whitelist. Проверки в `signIn` мало: она срабатывает
  один раз при входе, и удаление строки не завершало выданную сессию. У
  отозванного пользователя строки `Session` удаляются, а сессия возвращается без
  `user` — для приложения это то же самое, что её отсутствие.
- Отзыв стоит одного запроса по уникальному индексу на каждое чтение сессии.
  Кешировать нельзя: смысл проверки в том, что она срабатывает сразу.
- При создании пользователя идемпотентно создаётся default-пространство.
- Отказ по whitelist записывает в лог только короткий хеш email через `hashId`;
  исходный пользовательский идентификатор в лог не попадает.
- `/auth-error` показывает причину whitelist только для `AccessDenied`. Ошибки
  OAuth и конфигурации получают нейтральный текст без внутренних деталей.

### Пространства

- `Space` — верхний уровень организации списков пользователя.
- Default-пространство существует всегда, не удаляется и имеет ID `space_default_<userId>`.
- Допускается до пяти дополнительных пространств; их нормализованные имена уникальны для пользователя.
- Текущее пространство находится в URL `/{locale}/spaces/{spaceId}`; последнее выбранное хранится в httpOnly cookie `smart-lists-space`.
- Удаление дополнительного пространства удаляет его списки и группы, убирает размещённые там чужие списки и запускает фоновую очистку S3.
- Потолки на количество сущностей живут в `src/lib/limits.ts`: 200 списков и
  50 групп в пространстве, 500 пунктов верхнего уровня в списке, 100
  подпунктов у пункта. Пространства считаются отдельно — `MAX_CUSTOM_SPACES`
  в `src/lib/spaces.ts`, там потолок появился раньше.
- Эти числа ограничивают **один контейнер**, а не суммарный рост: их
  произведение — миллионы строк на пользователя. Они держат список в размере,
  при котором интерфейс и пересчёт позиций остаются отзывчивыми; границу
  хранилища задаёт суточный лимит мутаций, а не они.
- Проверка сделана обычным `count` без лока. Там, где счёт мал и точность
  важна (5 пространств, 5 вложений), в проекте используется строгий вариант с
  транзакцией; при 500 пунктах перебор на один-два ничего не значит, а
  параллельный флуд ограничивается суточным лимитом.

### Суточный бюджет мутаций

- Каждое действие, меняющее данные, списывает единицу бюджета: 1000 на
  пользователя в сутки по UTC (`src/lib/usage.ts`). Загрузка вложения стоит
  двух — `requestUpload` и `confirmUpload` обе пишут в БД.
- Счётчик в БД, а не в памяти процесса: Vercel исполняет Server Actions в
  нескольких экземплярах, и лимит в памяти рос бы вместе с нагрузкой — то есть
  отказывал бы ровно тогда, когда нужен.
- Инкремент атомарен (`upsert` + `increment` под уникальным ключом), при
  переборе откатывается. Тот же приём, что у квоты инсайтов.
- Что чем закрыто: бюджет ограничивает **темп** и потому закрывает рост
  хранилища, расход compute и квоту сообщений Pusher; потолки на сущности —
  только размер одного контейнера. Это разные защиты, подменять одну другой
  нельзя.
- `deleteItem` и `toggleItem` по существующему контракту ничего не возвращают
  клиенту, поэтому исчерпанный бюджет там виден не сразу: оптимистичное
  состояние держится до обновления страницы.
- Ряды `UserDailyUsage` старше 30 суток убираются лениво — при первой мутации
  новых суток, только свои ряды. Крона в проекте нет, и заводить его ради
  уборки счётчиков означало бы новый вход в систему и новую строку в модели
  угроз.

### Списки и совместный доступ

- `List` принадлежит одному владельцу и одному его пространству.
- `ListShare` даёт роль `EDITOR` и размещает список в пространстве получателя.
- Ключ `ListShare(listId, userId)` означает одно размещение списка на получателя.
- Default-space существующих пользователей создан миграцией, новых — событием
  Auth.js `createUser`; share использует детерминированный ID и составной FK,
  но не создаёт `Space` от имени получателя.
- Видимость определяет `listInSpaceWhere(userId, spaceId)`: собственный список в пространстве либо share, размещённый в нём.
- Редактор изменяет содержимое. Управление владением, удалением списка и участниками остаётся за владельцем.
- `ListGroup` — личная организация внутри пространства. Список может находиться в разных группах у разных пользователей.
- Сейчас изоляцию строк обеспечивает приложение через `listInSpaceWhere` и
  эквивалентные ownership-проверки; RLS в БД не включён. Согласован staged-
  переход: release migration вне Vercel, runtime без DDL, проверенный
  транзакционный контекст и только затем tenant-RLS. Прикладные фильтры
  сохраняются как обязательный первый слой.
- В Neon `dev` и `production` создана SQL-роль `smartlists_runtime` без ownership, DDL,
  `BYPASSRLS`, `CREATEROLE`, membership и доступа к migration metadata. С
  2026-08-13 Vercel Preview и Production используют её отдельные pooled
  credentials. Это ограничивает класс операций и таблиц, но ещё не изолирует
  строки одного tenant от другого.
- Прикладными объектами обеих веток владеет `smartlists_owner` без login;
  release workflow входят через `smartlists_migrator`. Production backup
  использует отдельную `smartlists_backup` с точечным `SELECT` и `BYPASSRLS`,
  без write, DDL и membership. `neondb_owner` остаётся только операторской
  break-glass/control-plane ролью и отсутствует в runtime и GitHub Actions.

### Записи и заметки

- `Item` принадлежит списку и может хранить автора добавления.
- Запись может быть подпунктом другой записи: `Item.parentId` при `null` означает пункт верхнего уровня. Вложенность ровно одна.
- Список и запись имеют plain-text заметку до 4000 символов. Разметка не разбирается: текст показывается как есть, переносы строк сохраняются.
- `noteVersion` обеспечивает optimistic concurrency; конфликт возвращает актуальную заметку и версию.
- Поиск учитывает названия и заметки, UI показывает фрагмент совпадения.
- Заметка сохраняется только явным действием: кнопкой или Ctrl/Cmd+Enter в textarea. Одиночный Enter переносит строку. Хоткей полностью эквивалентен кнопке — та же ожидаемая версия и то же условие активности, поэтому перезапись чужой правки остаётся отдельным действием.
- Заметка читается в карточке, но по высоте обрезается; полный текст и редактор открываются в диалоге. Признак — фактическое переполнение блока, а не длина текста: одна и та же заметка на узком экране занимает втрое больше строк. Черновик общий для встроенного редактора и диалога, поэтому переключение между ними не теряет набранное.
- Запись можно перенести или скопировать в другой список того же пространства. Перенос меняет `listId` у существующей строки, копия создаётся заново: `noteVersion` обнуляется, отметка о выполнении сбрасывается, автором становится копирующий. В обоих случаях запись встаёт в конец списка-получателя.
- Перенос доступен двумя путями: пункт меню с выбором списка и бросок записи на чужую карточку. Оба ведут в один и тот же `moveItemToList`, поэтому расходиться им нечем; жест умеет только перенос — копирование задаётся чекбоксом и в бросок не укладывается.

### Подпункты

- Связь самоссылочная и составная: `parent Item?` по `[parentId, listId]` на `[id, listId]`. Отсюда два свойства без единой строки кода: подпункт не может лежать в другом списке, чем родитель, а `onUpdate: Cascade` переносит подпункты за родителем при смене `listId` — перенос пункта в другой список остаётся одной записью в БД. `onDelete: Cascade` даёт «удалили пункт — ушли подпункты».
- Глубину составной ключ ограничить не может, поэтому «родитель обязан быть пунктом верхнего уровня» проверяет `addItem` и покрывает интеграционный тест.
- Отметка выполнения пункта **с подпунктами** производная: пункт выполнен ровно тогда, когда выполнены все его подпункты. У пункта без подпунктов значение своё — иначе пустое множество делало бы его выполненным. Правило собрано в `src/lib/item-tree.ts` (`buildItemTree`, `applyCompletion`) и повторено в Server Actions и гостевом хранилище.
- Клик по чекбоксу пункта означает «проставить это значение всем подпунктам», клик по подпункту пересчитывает родителя. Оба направления — одно правило, записанное с двух сторон, поэтому противоречивого состояния не существует.
- Собственное поле `isCompleted` у родителя всё же пишется как денормализованный кеш: отбор контекста для AI сортирует по нему прямо в SQL и дерева не собирает. На чтении в UI кеш не используется, поэтому расхождение пользователю не видно. Пересчёт живёт в `syncParentCompletion` и уходит в БД тем же батчем, что и правка подпункта.
- Родитель, оставшийся вовсе без подпунктов, сохраняет последнее значение: с этого момента оно снова его собственное.
- Счётчик «выполнено / всего» в шапке карточки считает только верхний уровень. Частично выполненный пункт при этом честно считается невыполненным — благодаря производной отметке счётчик не может разойтись с чекбоксами.
- Отдельный подпункт нельзя перенести или скопировать в другой список: он принадлежит родителю. Перенос пункта уводит подпункты каскадом, копирование воссоздаёт их с новыми ID, нулевой версией заметки и снятыми отметками.
- Компоненты получают записи **плоским** массивом с `parentId`, дерево собирается при рендере. Плоское представление нужно оптимистичному состоянию: обычные `map`/`filter` по одному массиву вместо рекурсии. Гостевое хранилище, наоборот, держит подпункты **вложенными** в родителя — там порядок задаёт сам массив, и «подпункты следуют за родителем» становится свойством структуры; одна вложенность закреплена самой Zod-схемой, у подпункта поля `subItems` нет.
- Подпункты рендерятся внутри `<li>` своего пункта, а не соседями. Это не только про отступ: при перетаскивании пункта framer двигает один DOM-узел, и подпункты едут с ним, ничего не зная о жесте. Их `data-testid` — `sub-item`, поэтому счёт записей в старых тестах не сбивается.
- Уровень читается по отступу и колонке номера; вертикальной линии слева у блока нет — она была третьим признаком того же самого.
- У подпункта колонка ручки перетаскивания сохраняется пустой, когда ручки нет, — как колонка номера у выполненной записи. Иначе отступ блока зависел бы от того, можно ли сейчас перетаскивать: единственный подпункт, выполненный подпункт и подпункт при активном поиске ручки не получают и прижимались бы вплотную к своему пункту.
- «Разбит на подпункты» — не признак записи и в БД его нет: пункт родительский ровно тогда, когда у него есть хотя бы один подпункт. Команда меню только открывает поле ввода; родительским пункт делает первый введённый подпункт, а удаление последнего возвращает его в обычные. Поле после Enter остаётся открытым и не ждёт сервера: подпункты набирают очередью, и флаг «сохраняется» глотал бы следующий ввод. От повтора того же текста защищает очистка поля.
- У выполненного пункта команды разбиения нет: разбивать сделанное незачем, а первый же подпункт вернул бы его в невыполненные.
- У подпункта в меню нет переноса в другой список и своего разбиения. Перемещение «выше/ниже» у подпунктов появится вместе с их перетаскиванием.
- Подтверждение удаления пункта называет число подпунктов: на экране они могут быть не видны, а отменить удаление нельзя.
- Блок подпунктов сворачивается. Состояний три, и различаются они источником: сохранённая ручная свёртка (`collapsedItems:<spaceId>`, у гостя `guest:collapsedItems`), автосворачивание выполненного блока и принудительный разворот при поиске. Приоритет — в обратном порядке: поиск сильнее автосворачивания, автосворачивание сильнее сохранённого набора.
- Выполненный блок сворачивается сам, а его разворот живёт только до перезагрузки и в localStorage не попадает: это следствие отметки, а не выбор пользователя. Поэтому снятие отметки возвращает блок в то состояние, которое пользователь выбирал для него как для активного.
- Свёрнутый блок показывает счётчик выполненных подпунктов: скрытые подпункты иначе не сосчитать. У раскрытого его нет — там те же числа читаются с самих строк. Тумблер «счётчик выполненных» в настройках управляет обоими счётчиками сразу: число по смыслу одно и то же, просто на разных уровнях, и два отдельных переключателя было бы нечем объяснить. Кнопка сворачивания от тумблера не зависит.
- При поиске кнопки сворачивания нет вовсе: блоки раскрыты принудительно, и нажатие меняло бы сохранённое состояние, ничего не меняя на экране. Тот же приём, что с пунктами перемещения.
- Свёрнутый блок размонтируется целиком, а не прячется стилем. У карточки списка тело оставлено в DOM ради анимации высоты; здесь анимации нет, и скрытая разметка только осталась бы доступной поиску по странице.
- Набор свёрнутых блоков живёт в `ListsContainer`: уборка исчезнувших ID требует знать все записи пространства, а отдельный `SmartList` видит лишь свой список. До `SmartList` он доходит контекстом `CollapsedItemsProvider` — пропс сбрасывал бы мемоизацию всех карточек при сворачивании одного блока, ровно как справочник списков.
- У каждого пункта своя `Reorder.Group` на подпункты. Это и есть механизм запрета «перенести подпункт к другому родителю»: областей столько же, сколько блоков, и жест не знает о существовании соседней. Отдельной проверки для этого не понадобилось.
- Вложенная группа внутри `Reorder.Item` родителя работает потому, что оба уровня начинают жест только с ручки (`dragListener={false}` + `useDragControls`). Иначе pointer на подпункте поднимал бы весь блок.
- Пункт перетаскивается вместе с блоком без единой строки кода: подпункты лежат в его DOM-узле, и framer двигает один элемент. Их позиции значимы внутри родителя и жестом верхнего уровня не затрагиваются.
- Уровни независимы по доступности жеста: список из одного пункта не мешает переставлять его подпункты, и наоборот. Условие одно на уровень — больше одной невыполненной записи и отсутствие поиска.
- Состояние жеста одно на компонент и помечено уровнем (`{ level, items }`, где `level` — `parentId`): одновременно идёт максимум один жест, и два отдельных состояния только разошлись бы.
- Пункты «Переместить выше/ниже» есть у обоих уровней и действуют в границах своего: у подпункта «выше» никогда не выносит его наружу. Это доступная с клавиатуры альтернатива жесту, ручка помечена `aria-hidden`.
- Превращения существующего пункта в подпункт и обратно нет и пока не планируется (решение 2026-08-08). Подпункты создают сразу под нужным пунктом, а команда «разбить на подпункты» этот сценарий закрывает; переосмысление уровня задним числом оказалось редким настолько, что не оправдывает отдельного Action с пересчётом отметок у обоих родителей.

### Порядок записей

- Порядок задаёт `Item.position` типа `Float`. Значимо только сравнение позиций внутри своей группы `(listId, parentId)`: у пунктов верхнего уровня сравниваются пункты списка, у подпунктов — подпункты одного родителя.
- Выборка сортируется по `position`, затем `createdAt` и `id`: тайбрейк делает порядок детерминированным при равных позициях.
- Порядок общий для всех участников списка. Персонального порядка нет.
- Новая запись получает `максимум + 1` по своему уровню. Максимум читается тем же запросом, что и проверка доступа: для подпункта это запрос к родителю, который заодно проверяет список, принадлежность родителя ему и запрет второго уровня.
- Перемещение выполняет `moveItem`: клиент присылает ID новых соседей, сервер читает их позиции из БД и пишет середину — одну строку. Целевой индекс не используется: он устаревает при параллельных изменениях. Соседи ищутся только среди записей своего уровня; сосед с другого уровня возвращает `stale`.
- Если середина не легла строго между соседями, уровень перенумеровывается целиком в транзакции. Ветка вырожденная и пишет отдельное сообщение в лог.
- Пропавший сосед возвращает `stale` без записи в БД; клиент откатывает оптимистичное перемещение.
- Отметка о выполнении и снятие отметки `position` не меняют. Выполненная запись выпадает из нумерации и уходит в нижний блок, снятие галки возвращает её на своё место.
- Видимый номер нигде не хранится: это индекс среди невыполненных записей, вычисляемый при рендере. Поэтому удаление и выполнение не требуют перенумерации.
- Гостевой режим порядок хранит порядком массива в `localStorage`; поля `position` там нет. Контракт с UI общий: массив записей всегда приходит упорядоченным.

### Порядок групп

- Личный порядок групп задаёт `ListGroup.position` типа `Float` внутри пары `userId + spaceId`; вкладка «Все» виртуальная и в БД не хранится.
- Новая группа получает `максимум + 1`. Выборки групп сортируются по `position`, затем `createdAt` и `id`; тот же массив используется вкладками, меню назначения списка, бейджами и диалогом переноса записи.
- `moveGroup` принимает ID новых соседей и проверяет группу, пространство и актуальность разрыва по БД. Обычно обновляется одна позиция; при исчерпании точности все группы пространства перенумеровываются в транзакции.
- UI использует dnd-kit с собственной стратегией многострочной раскладки: она пересчитывает flex-позиции с исходными ширинами вкладок и применяет только translate, поэтому вкладки разной ширины не деформируют текст и не перекрывают соседей. Ручка показывается только у активной группы, Keyboard Sensor даёт эквивалентное перемещение с клавиатуры, а при наведении на ручку и во время переноса вкладка в тёмной теме получает тёмный контрастный фон для видимости системного курсора. «Все» находится вне `SortableContext` и не перемещается.
- Гость хранит порядок самим массивом `groups` в `localStorage`; интерфейс и контракт `ListsApi` у обоих режимов одинаковы.

### Порядок списков в группах

- Порядок списка персонален и принадлежит его членству в конкретной группе, а не самому `List`: явная модель `ListGroupMembership` хранит `listId + groupId + position` и отображается на прежнюю таблицу `_ListGroupMembers`.
- Один список может состоять в нескольких группах с независимым порядком. Вкладка «Все» отдельного порядка не хранит и показывает доступные списки по `createdAt desc`, затем `id`.
- `moveListInGroup` использует тот же контракт соседей и midpoint/rebalance, что порядок записей и групп: сервер проверяет пользователя, пространство, доступность списка, членство и актуальность разрыва. Это личная организация, поэтому после ревалидации Pusher не отправляется.
- Добавление существующего списка в группу идемпотентно и ставит его в конец. Перетаскивание на другую вкладку именно добавляет членство, сохраняя исходную группу; если членство уже есть, действие ничего не меняет. Новый список, созданный при активной группе, появляется в её начале.
- DnD работает с единым плоским порядком до `splitIntoColumns`: колонки остаются только представлением и никогда не сохраняются. Поэтому перенос между колонками меняет тот же логический массив, что пункты «Переместить выше/ниже» в меню.
- Во вкладке «Все» ручки списков скрыты: глобальный порядок там не меняется, а ручка создавала ложное ожидание перестановки. Перетаскивание на другую вкладку группы доступно из конкретной активной группы; исходное членство сохраняется. Во время поиска DnD списков отключён, потому что видимое подмножество не задаёт однозначных соседей; после drop активная группа не переключается.
- За курсором движется компактный overlay. Исходная раскрытая карточка во время жеста полностью прозрачна: её полноразмерная проекция перекрывала соседей и мешала читать целевое место. Для свёрнутой карточки лёгкая проекция остаётся полезной и сохраняется. При переходе между колонками exit-копия карточки анимируется через `AnimatePresence mode="popLayout"`: она остаётся видимой на прежнем месте, но сразу исключается из flex-раскладки и не сдвигает остальные списки.
- Пока Server Action сохраняет новый порядок, повторный жест заблокирован, но ручки не удаляются из DOM, а остаются видимыми disabled. Это сохраняет геометрию заголовков без риска отправить параллельные перемещения с устаревшими соседями.
- Гость хранит независимый порядок в `group.listIds`. Старые данные только с `list.groupIds` мигрируют при чтении, сохраняя прежний глобальный порядок; устаревшие и повторные ID очищаются.

## Ключевые потоки

### Данные и realtime

- `ListsDataFetcher` параллельно загружает списки и личные группы точечными `select`.
- Клиентский UI работает через `ListsApi`; серверный провайдер добавляет `spaceId` и Pusher `socketId`.
- После мутации layout-level `revalidatePath` возвращает вкладке-автору свежий RSC payload.
- Клиент подписывается на `private-user-<userId>`; endpoint `/api/pusher/auth` разрешает только собственный канал.
- Событие `refresh` вызывает `router.refresh()`; вкладка-автор исключается по `socketId`.
- Ошибка Pusher логируется и не отменяет успешную запись в БД.
- Отклонённое имя Pusher-канала в лог не попадает: для корреляции сохраняются
  только короткие хеши пользователя и присланного имени канала.
- Мутация, затрагивающая два списка сразу, уведомляет участников обоих через `notifyListsMembers`: наборы получателей у списков разные, а объединение в один Set не даёт задвоенный `refresh` тем, кто состоит в обоих.

### Гостевой режим

- Включается только при `AppSetting` с ключом `guestModeEnabled` и значением `true`.
- httpOnly cookie `guest-mode` выбирает гостевой UI, данные находятся в `localStorage`.
- Отключение режима в БД или выход гостя не удаляет локальные данные.
- Гостю недоступны пространства, шаринг, Pusher, AI и вложения.
- Гостевая реализация `ListsApi` повторяет поддерживаемые базовые операции без обращения к БД.

### Вложения

- Разрешены PNG, JPEG, TXT и PDF до 10 MiB.
- Лимиты: 5 файлов на список и 20 файлов на загрузившего пользователя.
- Поток: создать `PENDING` -> загрузить напрямую по presigned POST -> проверить
  через `HeadObject` и сигнатуру содержимого -> отметить `UPLOADED`.
- `Content-Type` от клиента — это ярлык, а не факт: policy presigned POST лишь
  сверяет его с разрешённым значением, а `HeadObject` возвращает тот же ярлык.
  Поэтому `confirmUpload` дочитывает первые 16 байт объекта Range-запросом и
  сверяет их с сигнатурой (`matchesMagicBytes`). Непрочитанный префикс — отказ.
  У `text/plain` сигнатуры нет, для него проверки содержимого не существует и в
  S3 за байтами не ходим; ограничение осознанное, разобрано в `THREAT_MODEL.md`.
- Имя файла чистится `sanitizeFileName` прямо в `requestUploadSchema`:
  вырезаются управляющие, bidi- и невидимые символы, схлопываются пробелы. Имя
  показывается другим участникам и уходит в `Content-Disposition`, поэтому
  подмена расширения через `U+202E` вводила бы в заблуждение и в UI, и в диалоге
  сохранения. В адресации имя не участвует — object key генерирует сервер.
- `PENDING` старше 15 минут лениво переводятся в служебный
  `CLEANUP_PENDING` с DB-generated UUID-токеном и перестают занимать квоту.
  После успешного S3 delete helper удаляет только строки этих токенов; при
  сбое возвращает их в `PENDING`. Потерянный callback безопасно повторяется
  следующим запросом, а успешный S3 delete при сбое DB-finalize не создаёт
  битую ссылку. UI и download не видят `CLEANUP_PENDING`.
- В UI видны только `UPLOADED`; скачивание идёт по краткоживущему presigned URL.
- Удаление Prisma-строки не удаляет байты из S3 автоматически. У
  `deleteList`/`deleteSpace` уборка best-effort и без повтора, поэтому её сбой
  оставляет объект в бакете навсегда: `Expiration` на текущих версиях не задан.
  Самоудаления аккаунта в приложении нет — ручное удаление пользователя в Neon
  каскадом снесёт `Attachment` и осиротит все его файлы, ключи надо выбрать до.
- На бакетах вложений с 2026-08-10 включён versioning: `DeleteObject` создаёт
  delete marker, прежняя версия живёт 30 дней. Прав `DeleteObjectVersion` у
  ключа приложения нет — именно поэтому versioning здесь защита, а не
  формальность. `Expiration` для текущих версий не задан намеренно: у бэкапов
  он нужен, у пользовательских файлов означал бы пропажу по расписанию.

### AI-инсайты

- Server Action получает список из БД и проверяет доступ в текущем пространстве.
- Внешний сервис вызывается через `INSIGHTS_SERVICE_URL`. Аутентификация двухслойная и полностью на ID-токене: Cloud Run проверяет его до контейнера, а сервис — повторно и независимо, по подписи, `aud` и email вызывающего. Статических секретов на этом пути нет.
- Токен едет в обычном `Authorization`. Cloud Run принимает и `X-Serverless-Authorization`, но из него вырезает подпись перед передачей контейнеру — сервис получил бы claims, которые не может проверить. Из `Authorization` токен доходит целым, и второй слой становится настоящим.
- Токен выпускает `src/lib/gcp-auth.ts`: OIDC-токен Vercel меняется в Workload Identity Federation на право говорить от имени `vercel-insights-invoker`, тот выпускает ID-токен с audience равным базовому URL сервиса. Долгоживущих ключей нет. Провайдер пускает ровно одну среду — `production` этого проекта, — а у service account есть право звать единственный сервис `insights-api`.
- Без токена запрос не отправляется вовсе: Action возвращает ошибку конфигурации. Отправлять было бы бессмысленно — Cloud Run откажет гарантированно, — а в логе должна быть видна сломанная федерация, а не безымянный 403 из сети.
- Инсайты работают только в Production. В Preview и локально не задан `INSIGHTS_SERVICE_URL`, поэтому Action возвращает ошибку конфигурации, не доходя до сети; там же нет и OIDC-доступа к федерации. Это состояние существовало и до федерации; теперь оно закреплено ещё и в GCP, где условие провайдера не пускает никакую среду, кроме production.
- Дальше по цепочке секрета тоже нет: с 2026-08-10 сервис обращается к Anthropic не по ключу API, а по workload identity federation — предъявляет ID-токен своей личности в Cloud Run и получает доступ на десять минут. Подробности живут в репозитории сервиса; здесь это важно тем, что весь путь «браузер → Vercel → Cloud Run → Anthropic» не содержит ни одной строки, которую можно скопировать и переиспользовать.
- Лимит — 15 запросов на пользователя в сутки по UTC; счётчик `insights` в `UserDailyUsage`.
- Флаг `List.aiEnabled` разрешает или запрещает отправку содержимого списка.
  Умолчание — включено. Переключить может **любой участник**, а не только
  владелец: инсайт отправляет наружу и чужие заметки, и запретить это должен
  уметь тот, чьи данные уходят. Проверка стоит в `getListInsight`, а не только
  в интерфейсе, — скрытая кнопка обходится прямым вызовом Action.
- В панели инсайта постоянно висит строка о том, куда уходит содержимое. Она
  адресована участнику, который список не создавал: узнать об отправке ему
  больше неоткуда.
- Вопрос ограничен 500 символами.
- В контекст входят группы, в которых состоит список, — до 20 названий по 100
  символов. Только группы вызывающего: группы персональные, и без фильтра по
  `userId` личная организация одного участника расшаренного списка уехала бы в
  инсайт, который читает другой. Обрезка обязательна — групп в пространстве
  бывает до `MAX_GROUPS_PER_SPACE`, а сервис принимает 20.
- В контекст попадает до 50 пунктов верхнего уровня, до 100 подпунктов суммарно, до 10 заметок записей и до 8000 символов таких заметок. Лимиты пунктов и подпунктов раздельные: общий счёт означал бы разное для разных списков — один длинный блок вытеснял бы половину списка.
- Поле `items` в запросе сохраняет прежний смысл — записи верхнего уровня, — а подпункты приходят вложенным `sub_items`. Сервис, ничего не знающий о подпунктах, продолжает работать как работал: он просто не увидит нового поля.
- Подпункт попадает в контекст только вместе со своим пунктом: сам по себе он бессмысленнен и ещё и вводит модель в заблуждение. Заметка отброшенного подпункта считается пропущенной, а не отправленной, — сообщение пользователю говорит о фактически уехавшем.
- Отметка пункта в контексте считается по подпунктам, а не по полю строки: денормализованному кешу здесь доверять незачем.
- Ответ модели рендерится через `SafeMarkdown`: raw HTML не исполняется, а
  Markdown-ссылки и картинки превращаются в обычный текст. Это закрывает не
  только XSS, но и фишинговую навигацию, которую prompt injection могла вложить
  в ответ. Картинка отброшена по той же причине и с большим приоритетом: клик
  ей не нужен, браузер участника запросил бы чужой адрес сам. Атрибуты из
  ответа модели в разметку не переносятся вовсе, включая `title`: подсказка
  навигации не даёт, но показала бы произвольный текст от имени приложения.

## Локализация и интерфейс

- Locale prefix обязателен в URL; новый текст получает ключ во всех четырёх `messages/*.json`.
- При смене языка dev-консоль пишет `Encountered a script tag while rendering React component`. Это не дефект. `next-themes` рендерит внутри `ThemeProvider` инлайновый `<script>`, гасящий мигание темы до первой отрисовки; отключить его нечем — пакет экспортирует только `ThemeProvider` и `useTheme`. Провайдер лежит внутри сегмента `[locale]`, а переключатель делает клиентскую навигацию, поэтому поддерево пересоздаётся и скрипт монтируется в браузере, где не исполняется. Класс темы к этому моменту уже стоит на `<html>` и поддерживается эффектами, так что видимых последствий нет, а само сообщение живёт только в `react-dom-*.development.js` и в production не появляется. Лечится лишь подъёмом `<html>`, `<body>` и `ThemeProvider` в корневой layout, но там нет `params.locale` для `lang`, а ошибка в размещении скрипта вернёт мигание темы при каждой загрузке — обмен невыгодный.
- Стиль минималистичный, с нейтральной чёрно-белой основой и умеренными акцентами.
- Сохраняются мобильная адаптивность, светлая и тёмная темы, доступные подписи.
- Иконочные кнопки подписаны всплывающей подсказкой `src/components/ui/Tooltip.tsx`, а не нативным `title`: тот не показывается на тач-устройствах, не появляется с клавиатуры, и ни его задержкой, ни видом управлять нельзя. Подсказка ждёт 400 мс при наведении, при клавиатурном фокусе появляется сразу и только при `:focus-visible` — иначе она висела бы над меню, открытым собственным кликом. На тач-устройстве не показывается вовсе: `pointerenter` там приходит вместе с тапом.
- Текст подсказки становится и `aria-label` кнопки, если своего у неё нет: у иконочной кнопки остаётся один источник подписи, и разойтись им нечем. Свой `aria-label` остаётся там, где озвучка должна быть подробнее видимого текста («Действия со списком X» против «Действия»), а `labelsTrigger={false}` — там, где у кнопки есть видимый текст и подпись подменила бы его.
- Подсказка уходит порталом в `body` и позиционируется `fixed` по той же причине, что меню записи: строка списка на время layout-анимации получает трансформ и становится содержащим блоком даже для `fixed` потомков. Геометрия — чистая функция `src/lib/tooltip-anchor.ts`; сторона выбирается сверху, потому что кнопки здесь почти всегда открывают что-то под собой.
- Нативный `title` остался ровно там, где подсказка нужна у выключенной кнопки: выключенная кнопка pointer-событий не получает, и общий компонент о наведении на неё не узнал бы. Это кнопка вложений при исчерпанной квоте и меню записи во время сохранения.
- Настройки показа авторов, нумерации записей, счётчика выполненных и кнопки прокрутки хранятся в `localStorage`. Там же лежат активная группа — отдельным ключом на пространство (`activeGroupId:<spaceId>`), свёрнутые карточки (`collapsedLists:<spaceId>`) и свёрнутые блоки подпунктов (`collapsedItems:<spaceId>`) — и выбранная вкладка вместе со свёрнутостью верхней панели, общие для всех пространств (`activeTab`, `topPanel`). У гостя свои ключи с префиксом `guest:`.
- Верхнюю панель создания и поиска можно свернуть кнопкой в её правом верхнем углу. По умолчанию она раскрыта. Строка вкладок остаётся видна всегда, поэтому клик по вкладке в свёрнутом виде раскрывает панель: иначе переключение выглядело бы как сломанная кнопка. Содержимое при сворачивании размонтируется — и запрос поиска, и черновик названия живут в состоянии `ListsContainer`, терять нечего, а скрытая разметка осталась бы доступной поиску по странице. Восстановление сохранённого состояния после гидрации проходит без анимации: сервер отрисовал панель раскрытой, и 180 мс схлопывания в самом верху страницы сдвигали бы всё под ней. Анимацию включает первое переключение руками.
- Счётчик в шапке карточки считает только пункты верхнего уровня; подробнее — в разделе «Подпункты».
- В шапке карточки стоит счётчик «выполнено / всего». Он показывает прогресс, а не остаток: `N / M` в списке задач читается именно так, и обратный счёт сбивал бы с толку — отметка записи уменьшала бы первое число. Счётчик включён по умолчанию и выключается тумблером в настройках; тумблер один на раскрытые и свёрнутые карточки. У пустого списка счётчика нет.
- Заметка списка стоит выше скрываемого тела и потому доступна у свёрнутой карточки: она относится к списку целиком, как заголовок, а не к его содержимому. Полный текст открывается диалогом изнутри `NotePanel`; если бы блок лежал в теле, диалог унаследовал бы `visibility: hidden`. Сворачивание заметку закрывает — иначе свёрнутая карточка осталась бы высокой и это читалось бы как сбой. Пустую заметку по-прежнему создают из меню, поэтому кнопка в шапке появляется только когда текст есть.
- Карточку списка можно свернуть до шапки: остаются заголовок, счётчик и меню действий. Место счётчика от свёрнутости не зависит, поэтому при сворачивании он не прыгает.
- Сворачивание анимировано высотой (0.18s; при `prefers-reduced-motion` и на тач-устройствах — мгновенно). Анимация высоты заставляет браузер пересчитывать раскладку каждый кадр, и на телефоне этого бюджета не хватает: переход виден как рывок, а мгновенное сворачивание там выглядит лучше плохой анимации. Тело остаётся смонтированным, поэтому свёрнутая карточка получает `inert` и `visibility: hidden`: нулевая высота с обрезкой прячет содержимое только визуально, оставляя его в фокусе и в поиске по странице. `visibility` снимается на время анимации — иначе сворачивать было бы нечего. Обрезка тоже включается только на время анимации и в свёрнутом виде: у раскрытой карточки она срезала бы меню записи, выходящее за нижний край короткого списка.
- `overflow` и `visibility` тела переключаются прямой записью в DOM из колбэков анимации, а не через состояние React. Через состояние это стоило вчетверо: `setState` на старте анимации перерисовывал тело карточки вместе со `SmartList`, и первый кадр растягивался с 22 до 91 мс — клик, пауза, рывок. Ни одно из этих свойств на разметку React не влияет, поэтому ререндер там не нужен. Мемоизация `SmartList` как альтернатива проверялась замером и выигрыша не дала.
- Карточки разложены по трём колонкам вручную (`splitIntoColumns`), а не средствами `columns` или грида. Обе автоматические раскладки конфликтуют со сворачиванием: в multicol колонка карточки вычисляется из высот, поэтому изменение высоты перебрасывало соседей между колонками прямо посреди анимации; в гриде ряды выровнены по горизонтали, поэтому рядом со свёрнутой карточкой оставалась пустота во всю высоту раскрытой соседки. Здесь колонка задана порядковым номером и от высот не зависит вовсе.
- Разметка всегда содержит три куска, и оба крайних случая CSS собирает сам: ниже `xl` обёртки колонок получают `display: contents`, выпадают из раскладки, и карточки выстраиваются одним потоком в порядке DOM. Поэтому серверная разметка сразу верна и на телефоне, и на десктопе.
- Две колонки на среднем экране — единственный случай, который CSS собрать не может: из трёх кусков две колонки не склеить. Он включается после гидрации подпиской на медиа-запрос `MEDIUM_SCREEN_QUERY` через `useSyncExternalStore` (серверный снимок — всегда `false`). Это единственное место, где брейкпоинт продублирован в коде; значения в `rem`, как у Tailwind 4, иначе они разъедутся при нестандартном размере шрифта.
- Контейнер колонок имеет `key` по их числу. Без него при смене числа колонок карточка на мгновение оказывалась в DOM дважды: старая копия доигрывала исчезновение в прежней колонке, пока новая появлялась в соседней. Ключ размонтирует старое дерево мгновенно — `AnimatePresence` не анимирует собственное исчезновение.
- Раскладка идёт подряд идущими кусками, а не по остатку от деления: сохраняется порядок чтения сверху вниз по колонке, и соседи по вертикали остаются соседями по номеру — это понадобится, когда карточки можно будет перетаскивать. Следствие независимости от высот: колонки заканчиваются на разной высоте. Это персональная настройка отображения на устройство — набор ID лежит в `localStorage` ключом на пространство (`collapsedLists:<spaceId>`), в БД её нет и другим участникам расшаренного списка она не видна. ID исчезнувших списков отсеиваются при чтении, иначе набор рос бы вечно.
- Меню действий списка и меню записи закреплены `fixed` и раскрываются вверх, когда снизу не хватает места, — но только если вверху они действительно помещаются: у карточки на коротком экране может не хватать места с обеих сторон, и переворот увёл бы меню за верхнюю границу окна. Высота меню известна лишь после отрисовки, поэтому решение принимает layout-эффект — до того, как браузер нарисует кадр. Общая механика — в `src/lib/menu-anchor.ts`; там же разобрано, почему `fixed`, а не `absolute`.
- Меню действий списка позиционируется `fixed` по координатам своей кнопки, а не `absolute`. Первая причина историческая — `columns`-раскладка: Chrome учитывал высоту абсолютно спозиционированного потомка при балансировке колонок, и меню, вылезающее за нижний край карточки, выталкивало соседей в другую колонку. Меню записи пришло к `fixed` своим путём, ради независимости от трансформов строки. Меню групп остаётся `absolute`: оно раскрывается вверх внутри карточки и ни за какой край не выходит.
- При активном поиске свёрнутость игнорируется, а сохранённое состояние не меняется: карточка отрисована, только если совпадение в ней есть, и оставить её закрытой значило бы показать результат, на который нельзя посмотреть.
- Нумерация записей выключена по умолчанию и включается тумблером; порядок хранится независимо от неё.
- Порядок меняется перетаскиванием за ручку и пунктами «Переместить выше/ниже» в меню записи. Пункты меню — доступная с клавиатуры альтернатива, ручка помечена `aria-hidden`.
- Перетаскивание начинается только с ручки (`dragListener={false}` + `useDragControls`): иначе жест конфликтует с кликом по названию и скроллом страницы.
- При активном поиске порядок менять нельзя: пользователь видит подмножество записей, и перемещение перескакивало бы через скрытые.
- Ручку записи показывает более широкое условие, чем перестановку: «есть что переставлять ИЛИ есть куда унести». Единственная запись соседей не имеет, но утащить её в другой список хочется чаще всего, поэтому у неё ручка есть, а пунктов «выше/ниже» в меню по-прежнему нет. Выполненная запись ручки не получает: она нумерации не имеет и живёт в нижнем блоке, перенос ей доступен только через меню.
- Бросок записи на чужую карточку равен переносу через меню — тот же `moveItemToList` в режиме `move`. Набранный по дороге порядок внутри исходного списка не сохраняется: запись из него уезжает целиком, и вторая запись в БД ради исчезающего соседства бессмысленна.
- Цель броска ищет `src/lib/item-drop.ts` по геометрии карточек, а не библиотекой перетаскивания: `Reorder` односоставная и о соседней карточке не знает. Снимок прямоугольников делается на старте жеста и живёт до его конца — строки остаются в потоке, поэтому высоты карточек не меняются; учитывается только прокрутка страницы. `elementFromPoint` тут не годится вовсе: вынесенную строку framer рисует поверх соседей, и верхним элементом под курсором оказывалась бы она сама.
- Подсветка целевой карточки пишется прямо в DOM (`data-item-drop-active`): цель — чужая мемоизированная `ListCard`, и путь до неё через состояние перерисовывал бы все карточки на каждое пересечение границы. Тот же приём и по той же причине, что у тела карточки при сворачивании.
- Строка не покидает свой список: `dragConstraints` ограничивают жест тем `ul`, в котором строка живёт, — у пункта это группа списка, у подпункта группа его блока. Границы берутся из DOM (`parentElement` строки), а не пропом: так одно правило работает на обоих уровнях, а ref на группу подпунктов пришлось бы создавать по одному на пункт, чего в цикле по записям хук не позволяет. Выдаются они только на время жеста — почему, ниже. Без ограничения строка ехала за курсором через всю страницу, и при переносе в соседнюю карточку по ней нельзя было прочитать место броска. `dragElastic` уменьшен до `0.05`: доля берётся от всего перелёта, а он здесь измеряется сотнями пикселей.
- За курсором вне исходной карточки едет отдельная плашка: `Reorder.Group axis="y"` двигает строку только по вертикали, а карточки стоят колонками — в соседнюю она физически не попадёт. Теперь она и вертикально дальше своего списка не уходит, поэтому плашка остаётся единственным, что следует за указателем. Положение плашки тоже пишется в DOM: кадров жеста десятки в секунду, а перерисовывать по ним нечего.
- Пока идёт жест записи — любой, не только перенос, — страница не отвечает на наведение: `SmartList` ставит на `body` атрибут `data-item-dragging`, а правило в `globals.css` снимает `pointer-events` со всех его потомков. Иначе курсор по дороге зажигал бы вкладки, кнопки и чужие записи, хотя бросок туда ничего не делает; перечислить эти состояния поштучно нельзя — hover задан утилитами Tailwind у десятков элементов, а источник у них один. Жесту это не мешает: framer после старта слушает окно, а цель ищется по геометрии. Сам `body` из правила исключён, иначе с него перестал бы читаться курсор `grabbing`.
- Подпункт целей не ищет вовсе — он принадлежит родителю, и сервер такой перенос всё равно отклоняет. Автоскролла у жеста нет: карточка-получатель должна быть на экране, иначе остаётся меню.
- Поиск не подменяет массив записей: `ListsContainer` отдаёт список целиком и отдельно ID совпадений, иначе номера считались бы по подмножеству.
- Совпадение в подпункте показывает блок целиком. Это не послабление фильтра, а единственный вариант без лжи на экране: отметка родителя производная от подпунктов, а номера считаются как «x.y» по всем — скрытая часть сделала бы чекбокс и нумерацию необъяснимыми. Подсвечиваются при этом только настоящие совпадения.
- Границы жеста (`dragConstraints`) выдаются строке ТОЛЬКО на время жеста — от нажатия на ручку до его конца. Постоянно держать их нельзя: получив ref, framer вешает ResizeObserver на строку и на контейнер и при каждом изменении их размеров вызывает `scalePositionWithinConstraints`. Та сохраняет «прогресс» строки внутри границ, пересчитывает его под новый размер и пишет результат прямо в x/y строки. У покоящейся строки прогресс ненулевой, поэтому любое изменение высоты списка — раскрылась заметка, заметка ушла в редактор, раскрылся блок подпунктов — оставляло строкам inline `translateY` на десяток пикселей, и он не снимался никогда. Следствий два: строки съезжают и налезают друг на друга; меню записи перестаёт открываться на своём месте, потому что элемент с трансформом становится содержащим блоком даже для `position: fixed` потомков. Взвод на `pointerdown` даёт нужную перерисовку заранее — framer разрешает границы не в момент нажатия, а когда указатель прошёл порог жеста.
- Layout-проекция строк (`layout="position"`) оставлена включённой ради разъезда соседей во время жеста. Её цена — один кадр, на котором соседи ещё удерживаются на старом месте. Убрать этот кадр нечем: длительность перехода ни при чём (пружина ведёт себя так же), `layoutRoot` на группе не помогает, `layout` читается один раз при создании projection-узла, поэтому «включать только на время жеста» не работает, а выключенная навсегда проекция забирает и разъезд соседей. Затвор `useInstantLayoutTransition` съедается ближайшим обновлением проекции, а не тем, ради которого поставлен, и сам оставляет залипшие трансформы. Поэтому обезврежены последствия кадра: меню записи закреплено `fixed` (`src/lib/menu-anchor.ts`) и не запирается в контексте наложения строки, а фон строки непрозрачен и в тёмной теме, поэтому наложение перекрывает названия, а не смешивает их.
- `src/lib/drag-gate.ts` откладывает realtime-обновление на время жеста: `router.refresh()` посреди перетаскивания срывает его.
- Тот же затвор используется при перетаскивании групп: несвязанный realtime-refresh не должен размонтировать двумерный DnD-жест.

## Переменные окружения

Секретные значения никогда не записываются в репозиторий.

- БД: `DATABASE_URL` для runtime через PrismaPg остаётся в Vercel; Preview и
  Production используют разные credentials роли `smartlists_runtime` в своих
  ветках Neon;
  `DIRECT_URL` нужен только Prisma CLI — локально его загружает корневой `.env`,
  а Production и Preview migration jobs получают отдельные значения из
  GitHub Environments. Repository-level `DIRECT_URL` доступен только backup
  workflow и содержит credential `smartlists_backup`. `prisma generate` и
  Vercel build работают без него;
- Auth.js: `AUTH_SECRET`, `AUTH_GOOGLE_ID`, `AUTH_GOOGLE_SECRET`, при
  необходимости `AUTH_URL`; только в Vercel Preview дополнительно задан
  `AUTH_REDIRECT_PROXY_URL`;
- Pusher: `PUSHER_APP_ID`, `PUSHER_SECRET`, `NEXT_PUBLIC_PUSHER_KEY`, `NEXT_PUBLIC_PUSHER_CLUSTER`;
- S3: `S3_BUCKET_NAME`, `S3_REGION`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`;
- AI: `INSIGHTS_SERVICE_URL`;
- федерация в GCP (все четыре значения несекретные, задаются в Vercel только
  для Production — там же, где `INSIGHTS_SERVICE_*`): `GCP_PROJECT_NUMBER`,
  `GCP_WORKLOAD_IDENTITY_POOL_ID`, `GCP_WORKLOAD_IDENTITY_POOL_PROVIDER_ID`,
  `GCP_SERVICE_ACCOUNT_EMAIL`;
- логирование: необязательный `LOG_LEVEL`, по умолчанию `info`.

## Разделение сред

Разработка не имеет доступа к боевым данным. Разведены три сервиса, способные их изменить; для каждого production, Preview на Vercel и локальная среда используют свой ресурс.

- БД — отдельная ветка Neon. Локальные команды Prisma получают `DIRECT_URL` из
  корневого `.env`, поэтому боевой URL в нём означал бы работу с production.
  Runtime production URL хранится в Vercel, прямые migration URL — в GitHub
  Environments, а отдельный backup URL — в repository secret. После
  проверенных cutover приложение и Vercel build не получают прямых credentials;
  GitHub workflows используют только ограниченные migrator/backup роли.
- Auth.js — разные `AUTH_SECRET` и Google OAuth clients для Production и
  Preview. Все Preview deployments делят только Preview-секрет и Preview OAuth
  client. Постоянная ветка `preview` служит redirect proxy Auth.js и не
  предназначена для разработки функций. Её стабильный URL —
  `https://smart-lists-git-preview-kirills-projects-ed9814e1.vercel.app`;
  Google callback заканчивается на `/api/auth/callback/google`, а
  Preview-only `AUTH_REDIRECT_PROXY_URL` — на `/api/auth`. Auth.js добавляет
  provider path сам и возвращает браузер на исходный Preview deployment.
  После успешного CI на `main` workflow `sync-preview.yml` берёт ровно
  проверенный SHA и синхронизирует ветку, если относительно `preview` менялись
  auth routes, Auth.js, runtime-зависимости proxy или конфигурация деплоя.
  Обычные UI-изменения нового Preview deployment этой ветки не создают.
- S3 — отдельный бакет и отдельный IAM-пользователь. Причина: база хранит только ключи, файл существует в одном экземпляре, и на общем бакете удаление вложения в dev-среде стирало боевой файл. Политика dev-пользователя повторяет боевую и ограничена префиксом `lists/*`: расхождение в правах дало бы ключ, работающий локально и падающий в production.
- Pusher — отдельное приложение. Уведомления идут в каналы `private-user-<id>`, а ID пользователей в копии базы совпадают с боевыми, поэтому на общем приложении локальные мутации дёргали вкладки реальных пользователей.
- AI-сервис к нему обращается только Production. Разделять сам сервис не требуется: суточный лимит считается в `UserDailyUsage`, у каждой базы счётчик свой. Но переменные `INSIGHTS_SERVICE_*` заданы лишь в Production, поэтому Preview и локальная среда к нему не ходят вовсе — и федерация в GCP закреплена так же, на одну среду. Следствие: инсайты — единственный поток, где Preview намеренно не повторяет Production, и проверять их можно только на боевом окружении (решение 2026-08-09).

Следствие для пересоздания dev-ветки: приехавшие из прода строки `Attachment` указывают на объекты боевого бакета, которых в dev-бакете нет. Такие вложения локально не открываются, а их удаление обращается к несуществующему ключу и боевой файл не затрагивает.

## Заголовки безопасности

Задаются в `next.config.ts` через `headers()` на `/:path*`, поэтому попадают на
все ответы, включая `/api/*` и `/auth-error` — оба исключены из матчера
`proxy.ts`. Состав закреплён тестами в `test/next-config.test.ts`.

`X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`,
`Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy`
(camera/microphone/geolocation отключены), `Strict-Transport-Security` на год.

Content Security Policy заведена частично — только директивы, не требующие
per-request nonce:

```
base-uri 'self'; object-src 'none'; frame-ancestors 'none';
form-action 'self' https://accounts.google.com
```

- `default-src`, `script-src`, `style-src`, `connect-src` и `img-src`
  намеренно НЕ заданы. Без `default-src` браузер эти типы ресурсов не
  ограничивает, поэтому заголовок статический и не влияет на рендеринг.
- `accounts.google.com` в `form-action` обязателен. Проверено в Chromium:
  без JS форма входа уходит обычным POST, Auth.js отвечает редиректом на
  Google, и Chrome применяет `form-action` к цели редиректа, а не только к
  `action` формы. С `form-action 'self'` вход ломается. В Preview цель та же —
  redirect proxy Auth.js подменяет только `redirect_uri`
  (`@auth/core/lib/actions/signin/authorization-url.js`), а не адрес, куда
  уходит браузер.
- `frame-ancestors 'none'` дублирует `X-Frame-Options`; старый заголовок
  оставлен для браузеров, не знающих директиву.

### Почему политика на этом остановлена

`script-src` с nonce сознательно не вводится. Разбор 2026-07-30 показал, что
соотношение пользы и цены плохое, причём по двум причинам, каждая из которых
опровергает ходовой аргумент:

- **От скомпрометированной зависимости `script-src` не защищает вообще.**
  Вредоносный пакет попадает в собственный бандл и отдаётся с того же origin:
  `'self'` его пропускает, а с `nonce` + `'strict-dynamic'` его подгрузит
  доверенный bootstrap и передаст доверие дальше. От этой угрозы работают
  `connect-src` и `img-src`, которым nonce не нужен.
- **Довод «nonce переводит страницы в динамический рендеринг» здесь неверен.**
  `generateStaticParams` в проекте нет, боевые ответы идут с
  `Cache-Control: private, no-cache, no-store` — всё и так динамическое.

Остаётся единственная реальная польза `script-src`: защита от будущей
регрессии с инъекцией разметки. Она закрыта дешевле — правилами ESLint
(`react/no-danger` и запрет импорта `rehype-raw`, см. `eslint.config.mjs`),
которые ловят ту же ошибку в CI до мержа. Тесты — `test/eslint-xss-guard.test.ts`.

Цена nonce, если к нему всё же вернутся, — четыре точки интеграции:
`next-themes` рендерит инлайновый `<script>` и требует передачи пропа `nonce`
(иначе мигание темы при каждой загрузке); матчер `proxy.ts` исключает
`/auth-error` и `/api`, куда nonce не доедет; Vercel Toolbar в Preview тянет
`vercel.live` и потребует условного по среде allowlist, из-за чего Preview
перестанет быть точной репетицией Production; `style-src` всё равно потребует
`'unsafe-inline'`.

`connect-src` и `img-src` тоже не введены: польза ограничена (эксфильтрация
через навигацию не блокируется ни одной работающей директивой, а вредоносный
скрипт может просто дёргать Server Actions с того же origin), а хост S3
и кластер Pusher берутся из env и различаются между Production, Preview и
локальной средой — статический заголовок пришлось бы собирать из build-time
env, и ошибка тихо сломала бы загрузку вложений, которая автотестами не
покрыта.

Инвентаризация источников на момент 2026-07-30, если политику будут
расширять: `img-src` — `flagcdn.com` (флаги локалей); `connect-src` — Pusher
(`wss://ws-<cluster>.pusher.com`, `https://sockjs-<cluster>.pusher.com`) и хост
S3-бакета (клиент делает прямой POST в presigned URL); `font-src 'self'`
(`next/font` самохостит Geist); `style-src` потребует `'unsafe-inline'` —
React прокидывает `style={{...}}`, framer-motion пишет inline-стили.
AI-сервис вызывается с сервера и в политику не входит. `pusher-js` и
`framer-motion` не используют `eval`/`new Function`, поэтому `'unsafe-eval'`
не нужен.

### Интеграционные тесты

Server Actions проверяются против настоящего PostgreSQL — это единственный
способ покрыть права доступа, привязку к пространству, каскады и concurrency.
Файлы — `test/integration/*.int.test.ts`, конфиг — `vitest.integration.config.ts`
(отдельный от юнитов: те быстрые и без зависимостей, эти требуют базы).

БД поднимается в Docker (`docker-compose.test.yml`, порт 5433, данные в tmpfs).
`test/integration/global-setup.ts` ждёт готовности и накатывает миграции тем же
`prisma migrate deploy`; перед этим — защита: миграции применяются, только если
имя базы содержит `test` (обход — `ALLOW_NON_TEST_DB=1`). Между тестами
`beforeEach` делает `TRUNCATE ... CASCADE`, поэтому файлы гоняются
последовательно (`fileParallelism: false`). Внешние сервисы замоканы в
`test/integration/setup.ts`: сессия управляется через `setSessionUser`, `after`
копит колбэки и запускается вручную через `flushAfter` (Pusher/S3-побочки
проверяются как факт), Pusher и сетевые функции S3 — no-op со шпионами, а
чистый `buildAttachmentKey` оставлен настоящим. Фикстуры — `factories.ts`.

Покрыто: контроль доступа (владелец vs редактор), изоляция пространств,
жизненный цикл шаринга, CRUD пространств (лимит, каскад, защита default),
удаление и переименование списка владельцем — успешный путь отдельно от
отказа: каскад на записи, сбор ключей вложений до удаления (после каскада их
уже не взять), best-effort уборка S3 и уведомление получателей, собранных
заранее,
порядок записей `moveItem`, списков `moveListInGroup` и групп `moveGroup`,
включая независимость групп, проверку устаревших соседей и ветку
перенумерации, перенос и копирование между списками,
concurrency заметок по `noteVersion`, группы и вложения
(two-phase-загрузка, квоты на список и пользователя, ленивая уборка PENDING,
очистка имени файла, отказ по несовпавшей сигнатуре и fail-closed при
непрочитанном содержимом),
потолки на количество сущностей и суточный бюджет мутаций — включая
перечисляющий тест, который требует бюджет от каждого мутирующего действия,

между списками и целостность составного ключа), а также контекст AI-инсайта:
вложенные `sub_items`, раздельные лимиты уровней, производная отметка пункта
и честный счётчик отправленных заметок (`fetch` подменяется шпионом, сам
сервис не поднимается). Отдельно — гейт гостевого режима `isGuestModeEnabled`:
вход открывает только точное значение `true`, а отсутствие строки, постороннее
значение и сбой запроса одинаково означают запрет.

### E2E-тесты

Playwright гоняет настоящий браузер против production-сборки приложения
(`next build && next start`, порт 3100) и отдельной базы в Docker
(`docker-compose.test.yml`, профиль `e2e`, порт 5434). Файлы —
`test/e2e/*.e2e.ts`, конфиг — `playwright.config.ts`.

Вход через Google не выполняется: тест создаёт строку `Session` — ту же, что
пишет Prisma Adapter при настоящем входе, — и кладёт её токен в cookie
`authjs.session-token`. Приложение такую сессию не отличает от полученной по
OAuth. Следствие: колбэк `signIn` E2E не покрывает — но whitelist покрывает,
через колбэк `session`: тест удаляет строку `AllowedEmail` у своего
пользователя и проверяет, что следующий переход уводит на экран входа. По той
же причине фабрика обязана создавать эту строку — без неё тестовый
пользователь разлогинивается на первом запросе.

Изоляция держится на данных, а не на очистке: каждый тест работает под
собственным пользователем со своим пространством, поэтому файлы идут
параллельно. `TRUNCATE` выполняется один раз в `global-setup.ts` — посреди
прогона он снёс бы данные соседнего теста. Из этого следует правило для новых
проверок: любой запрос к БД в ассерте фильтруется по своим `listId`/`userId`;
`count()` по всей таблице поймает чужие строки. Единственное общее состояние —
`AppSetting` гостевого режима, поэтому `guest.e2e.ts` объявлен serial.

Селекторы — `data-testid`. Текст в них не годится: интерфейс переводится на
четыре языка, и тест ломался бы при правке перевода. Дополнительный слой —
хелпер `visible()`: на время переходов и анимаций в DOM остаётся скрытая копия
поддерева, и strict mode Playwright считает её вторым совпадением.

#### Зависший E2E-сервер на Windows

На Windows Playwright иногда завершает тесты, но не останавливает дочерний
`next start`: команда висит после строки `N passed`, а порт `3100` остаётся
занят. Раньше локальный `reuseExistingServer` молча подключал следующий прогон
к этому процессу, поэтому свежие тесты могли проверять предыдущую `.next`-
сборку. Теперь переиспользование по умолчанию выключено и включается только
явно через `E2E_REUSE_SERVER=1`.

Если E2E завис после успешного результата или сообщает занятый порт:

1. Найти слушающий PID: `netstat -ano | findstr :3100`.
2. Проверить команду процесса:
   `Get-CimInstance Win32_Process -Filter "ProcessId = <PID>" | Select-Object ProcessId, ParentProcessId, CommandLine`.
3. Только если `CommandLine` указывает на `smart-lists` и `next start`, остановить
   именно этот PID: `Stop-Process -Id <PID> -Force`.
4. Повторить прогон. `E2E_SKIP_BUILD=1` использовать только после успешного
   `npm run build`; иначе Playwright намеренно запустит имеющуюся старую сборку.

Если в выводе уже есть `N passed`, зависла лишь уборка web-server, а не сами
тесты. В CI проблема не наблюдалась: там существующий сервер никогда не
переиспользуется, а процесс живёт внутри одноразового Linux-раннера.

Покрыто: гейты и редиректы (локаль, чужое и несуществующее пространство, cookie
последнего пространства), жизненный цикл списка и записи с проверкой после
перезагрузки, порядок записей перетаскиванием и пунктами меню, запрет
перетаскивания за название и при активном поиске, заметки (сохранение, переход
в диалог по переполнению, общий черновик, конфликт версий, Ctrl+Enter против
одиночного Enter), поиск по названиям,
записям и заметкам обоих уровней — заметка списка оставляет все его записи,
заметка записи сужает карточку до неё одной, — сворачивание карточки с памятью после перезагрузки, его
стык с поиском, сворачивание верхней панели с памятью после перезагрузки и

уход выполненных вниз своей секции и всего блока — вниз списка, счётчик по

подпункта и его собственная заметка; отдельным файлом — свёртывание блоков:
ручная свёртка с памятью после перезагрузки, автосворачивание выполненного
блока и несохраняемость его разворота, общий с шапкой тумблер счётчика, стык

выполненных; и ещё одним — перенос записи броском на чужую карточку: попадание
с подсветкой цели, плашкой за курсором, погашенным на время жеста откликом
страницы на наведение и сменой `listId` без копии, промах

целей у подпункта; и последним — тот же перенос через меню и диалог выбора
списка: копирование с сохранением записи в исходном списке, перенос без
чекбокса, недоступный для выбора список-источник и двухшаговый выбор через
группу со стрелкой назад. Копирование и перенос проверяются парой намеренно:
поодиночке ни один из тестов не отличает один режим от другого, а
интеграционные тесты инвертированный чекбокс не видят — Action выполняет
переданный ему режим честно. Отдельным файлом — раскладка строк при смене их
высоты: переход заметки в режим редактирования не оставляет на строках ни одного
смещения и меню открывается на своём месте у каждой записи; открытое меню
остаётся поверх следующих строк; у нижнего края окна оно раскрывается вверх и
целиком помещается в окне; фон строки непрозрачен в обеих темах. Перекрытие меню
замеряется по кадрам через `requestAnimationFrame`: артефакт живёт ровно столько,
сколько доигрывает layout-анимация, и одиночная проверка после клика прошла бы
мимо него. И последним — всплывающие подсказки: показ по наведению и уборка
вместе с курсором, отсутствие подсказки после клика мышью (её сдерживает
`:focus-visible`), показ по настоящему Tab и уборка по Escape, а также две
стороны подписи — текст подсказки становится `aria-label` кнопки, но свой,
более подробный, не подменяет.

Не покрыто намеренно: OAuth-хендшейк Google, доставка realtime через Pusher,
вложения (нужен S3-совместимый сервис) и AI-инсайты (нужен внешний сервис). У
последних интеграционный тест всё же есть — он проверяет не ответ модели, а
сформированный запрос: `fetch` подменяется шпионом. У Pusher вне проверки

### CI

`.github/workflows/ci.yml` запускает четыре job на каждый push обычной ветки и
на pull request из форка или от Dependabot. Для внутренних пользовательских
веток pull_request-прогон пропускается как дубль push-прогона; для
`dependabot/**`, наоборот, push отключён, потому что бот его не создаёт, и
используется pull_request-прогон.
`checks` — lint, typecheck, юнит-тесты и `npm run build` с заведомо нерабочими
`DATABASE_URL`, `AUTH_SECRET`, `NEXT_PUBLIC_PUSHER_*` (сборка в БД не ходит и
`DIRECT_URL` не получает).
`integration` — интеграционные тесты против service-контейнера `postgres:17`;
`prisma migrate deploy` там применяется только к эфемерной базе раннера.
`e2e` — Playwright с Chromium против такого же service-контейнера на порту 5434;
при падении отчёт со скриншотами и видео выгружается артефактом. Загрузка
браузера и установка системных пакетов разнесены по разным шагам: apt в раннере
уходит на зеркало Ubuntu, которое периодически не отвечает и вешает шаг молча.
Шаг системных зависимостей необязателен (`continue-on-error`, свой потолок),
потому что на образе `ubuntu-24.04` он доставляет только шрифты — библиотеки
Chromium там уже есть, а скриншотных сравнений в E2E нет. У job есть
`timeout-minutes`: зависший шаг обязан падать сам, иначе production migration
ждёт его через `needs` и не получает отказа.
`secrets` — gitleaks по всей истории (`fetch-depth: 0`), потому что секрет,
добавленный и удалённый внутри одного PR, остаётся в промежуточных коммитах.

`ENABLE_PREVIEW_MIGRATION=true`. Подготовленные job берут два secrets —
`DIRECT_URL` и `EXPECTED_DATABASE_HOST` — из GitHub Environment, сверяют exact
direct host и запрещают pooler. После доказанного go/no-go `vercel.json`
использует обычный `npm run build`; миграции в Vercel build больше не входят.

официального checksum-файла релиза. Новая версия требует одновременного
осознанного обновления версии и checksum.

Репозиторий публичный. Отсюда два следствия: минуты Actions не тарифицируются,
а логи прогонов и артефакты доступны всем — выгружать в них содержимое базы или
пользовательские данные нельзя. Секреты в логах GitHub маскирует сам, но
печатать их намеренно нельзя тем более.

Установка в CI — `npm ci`, поэтому `package-lock.json` обязан быть источником
истины для Linux. Разработка идёт на Windows, но `npm install` там записывает в
lock только Windows-специфичные платформенные пакеты и опускает вложенные
optional-зависимости Linux-вариантов (`@emnapi/*` у wasm-фолбэков). С таким
lock `npm ci` на раннере падает с «Missing … from lock file».

Чинить нужно на Linux, но не регенерацией с нуля: `rm package-lock.json`
поднимает все плавающие (`^`) зависимости до свежих версий и меняет поведение
инструментов (так `eslint-plugin-react-hooks` прыгнул 7.0.1 → 7.1.1 и
завалил lint новым правилом). Правильный рецепт — в Linux-контейнере
(`node:24`, как в CI и в сборке Vercel) выполнить обычный `npm install` поверх
существующего lock: он уважает уже закреплённые резолюции и лишь дописывает
недостающее. Затем проверить, что `npm ci --ignore-scripts` там проходит.
Устанавливать в контейнере нужно в его собственную ФС, а не в смонтированный
Windows-том: bind-mount в Docker Desktop пишет тысячи файлов мучительно долго.

### Бэкап базы

`.github/workflows/backup.yml` ежедневно снимает `pg_dump -Fc` и кладёт его в
отдельный приватный S3-бакет в `ap-northeast-1` под ключом
`backups/smart-lists-<дата JST>.dump`. Расписание — `0 15 * * *`, то есть
полночь по Токио; GitHub запускает cron с задержкой до полутора часов.

Workflow подключается к Production как `smartlists_backup`: роль имеет только
`CONNECT`, `USAGE public`, `SELECT` и `BYPASSRLS`, необходимый для полного дампа
после включения RLS; write, DDL и membership отсутствуют. Cutover 2026-08-13
подтверждён восстановлением свежего Production dump в изолированную PostgreSQL
17 БД и успешным GitHub run `31681055043` на main SHA `53bcba40`.

Дамп содержит email пользователей, OAuth-токены `Account` и всё содержимое
списков, поэтому артефакты Actions для него не годятся: их может скачать любой,
у кого есть доступ на чтение репозитория, а репозиторий планируется публиковать.
Бакет заведён отдельно от бакета вложений, чтобы ключи в GitHub давали право
только на запись бэкапов и не открывали доступ к файлам пользователей.

Доступ к AWS выдаётся через OIDC, долгоживущих ключей в репозитории нет.
GitHub подписывает id-токен, роль `smart-lists-backup-ci` меняет его на временные
креды и разрешает единственное действие — `s3:PutObject` в `backups/*`. Trust
policy сверяет `sub`, поэтому форки и pull request'ы кредов не получают.

GitHub выдаёт `sub` в формате immutable subject claims — с числовыми
идентификаторами вместо имён: `repo:kzhirikhin@175179463/smart-lists@1150633776:ref:refs/heads/main`.
Человекочитаемый вариант `repo:owner/repo:...` не совпадёт, и обмен упадёт с
`AccessDenied` без объяснения причины; фактический `sub` виден в CloudTrail в
поле `userName` события `AssumeRoleWithWebIdentity`. Плюс формата в том, что
переименование репозитория или владельца ничего не ломает: ID неизменны. Условие
нужно править только при смене ветки, с которой идёт запуск.

Секреты репозитория: `BACKUP_S3_BUCKET`, `BACKUP_AWS_ROLE_ARN` и `DIRECT_URL`
роли `smartlists_backup`. Срок хранения задаётся lifecycle-правилом бакета
`expire-backups-30d`, а не workflow.

Производное значение превращает оба правила в одно, снимает гонку между участниками, отмечающими последние подпункты одновременно, и делает нумерацию `x.y` согласованной по построению — выполненный пункт не может иметь невыполненных подпунктов, поэтому `x.1` при отсутствующем `x` недостижимо. Цена — клик по чекбоксу пункта меняет отметки всех подпунктов, в том числе снимает их; это принято сознательно ради «закрыть весь блок одним кликом».
