## Назначение

Smart Lists — локализованное веб-приложение для личных и совместных списков. Пользователь организует списки по пространствам и группам, совместно редактирует записи и заметки, прикрепляет файлы и может запрашивать AI-инсайт.

Есть два режима данных:

- авторизованный — PostgreSQL, совместный доступ, Pusher, S3 и AI;
- гостевой — локальные данные браузера без шаринга, realtime, вложений и AI.

## Актуальный стек

- Next.js `16.1.4`, App Router, Server Components и Server Actions;
- React `19.2.3`, TypeScript strict, Tailwind CSS 4, Framer Motion;
- Auth.js v5 с Google OAuth и Prisma Adapter;
- Prisma `6.19.2` и PostgreSQL;
- `next-intl`: `ru`, `vi`, `en`, `ja`; default locale — `en`;
- Pusher, приватный S3-бакет и внешний FastAPI-сервис AI-инсайтов;
- Zod, Pino, React Hot Toast, `next-themes` и `lucide-react`;
- React Markdown — только для ответов AI-инсайтов; остальной пользовательский текст разметку не разбирает;
- Vercel region — `sin1`.

Точные версии всегда смотри в `package.json` и `package-lock.json`.

## Модель данных и права доступа

### Авторизация

- Вход выполняется через Google OAuth.
- Email должен существовать в `AllowedEmail`; whitelist управляется напрямую в БД.
- Сессии хранятся через Prisma Adapter; callback добавляет `session.user.id`.
- При создании пользователя идемпотентно создаётся default-пространство.

### Пространства

- `Space` — верхний уровень организации списков пользователя.
- Default-пространство существует всегда, не удаляется и имеет ID `space_default_<userId>`.
- Допускается до пяти дополнительных пространств; их нормализованные имена уникальны для пользователя.
- Текущее пространство находится в URL `/{locale}/spaces/{spaceId}`; последнее выбранное хранится в httpOnly cookie `smart-lists-space`.
- Удаление дополнительного пространства удаляет его списки и группы, убирает размещённые там чужие списки и запускает фоновую очистку S3.

### Списки и совместный доступ

- `List` принадлежит одному владельцу и одному его пространству.
- `ListShare` даёт роль `EDITOR` и размещает список в пространстве получателя.
- Ключ `ListShare(listId, userId)` означает одно размещение списка на получателя.
- Видимость определяет `listInSpaceWhere(userId, spaceId)`: собственный список в пространстве либо share, размещённый в нём.
- Редактор изменяет содержимое. Управление владением, удалением списка и участниками остаётся за владельцем.
- `ListGroup` — личная организация внутри пространства. Список может находиться в разных группах у разных пользователей.

### Записи и заметки

- `Item` принадлежит списку и может хранить автора добавления.
- Список и запись имеют plain-text заметку до 4000 символов. Разметка не разбирается: текст показывается как есть, переносы строк сохраняются.
- `noteVersion` обеспечивает optimistic concurrency; конфликт возвращает актуальную заметку и версию.
- Поиск учитывает названия и заметки, UI показывает фрагмент совпадения.
- Заметка читается в карточке, но по высоте обрезается; полный текст и редактор открываются в диалоге. Признак — фактическое переполнение блока, а не длина текста: одна и та же заметка на узком экране занимает втрое больше строк. Черновик общий для встроенного редактора и диалога, поэтому переключение между ними не теряет набранное.
- Запись можно перенести или скопировать в другой список того же пространства. Перенос меняет `listId` у существующей строки, копия создаётся заново: `noteVersion` обнуляется, отметка о выполнении сбрасывается, автором становится копирующий. В обоих случаях запись встаёт в конец списка-получателя.

### Порядок записей

- Порядок задаёт `Item.position` типа `Float`. Значимо только сравнение позиций между собой.
- Выборка сортируется по `position`, затем `createdAt` и `id`: тайбрейк делает порядок детерминированным при равных позициях.
- Порядок общий для всех участников списка. Персонального порядка нет.
- Новая запись получает `максимум + 1`. Максимум читается тем же запросом, что и проверка доступа.
- Перемещение выполняет `moveItem`: клиент присылает ID новых соседей, сервер читает их позиции из БД и пишет середину — одну строку. Целевой индекс не используется: он устаревает при параллельных изменениях.
- Если середина не легла строго между соседями, список перенумеровывается целиком в транзакции. Ветка вырожденная и пишет отдельное сообщение в лог.
- Пропавший сосед возвращает `stale` без записи в БД; клиент откатывает оптимистичное перемещение.
- Отметка о выполнении и снятие отметки `position` не меняют. Выполненная запись выпадает из нумерации и уходит в нижний блок, снятие галки возвращает её на своё место.
- Видимый номер нигде не хранится: это индекс среди невыполненных записей, вычисляемый при рендере. Поэтому удаление и выполнение не требуют перенумерации.
- Гостевой режим порядок хранит порядком массива в `localStorage`; поля `position` там нет. Контракт с UI общий: массив записей всегда приходит упорядоченным.

## Ключевые потоки

### Данные и realtime

- `ListsDataFetcher` параллельно загружает списки и личные группы точечными `select`.
- Клиентский UI работает через `ListsApi`; серверный провайдер добавляет `spaceId` и Pusher `socketId`.
- После мутации layout-level `revalidatePath` возвращает вкладке-автору свежий RSC payload.
- Клиент подписывается на `private-user-<userId>`; endpoint `/api/pusher/auth` разрешает только собственный канал.
- Событие `refresh` вызывает `router.refresh()`; вкладка-автор исключается по `socketId`.
- Ошибка Pusher логируется и не отменяет успешную запись в БД.
- Мутация, затрагивающая два списка сразу, уведомляет участников обоих через `notifyListsMembers`: наборы получателей у списков разные, а объединение в один Set не даёт задвоенный `refresh` тем, кто состоит в обоих.

### Гостевой режим

- Включается только при `AppSetting` с ключом `guestModeEnabled` и значением `true`.
- httpOnly cookie `guest-mode` выбирает гостевой UI, данные находятся в `localStorage`.
- Отключение режима в БД или выход гостя не удаляет локальные данные.
- Гостю недоступны пространства, шаринг, Pusher, AI и вложения.
- Гостевая реализация `ListsApi` повторяет поддерживаемые базовые операции без обращения к БД.

### Вложения

- Разрешены PNG, JPEG, TXT и PDF до 10 MiB.
- Лимиты: 5 файлов на список и 20 файлов на загрузившего пользователя.
- Поток: создать `PENDING` -> загрузить напрямую по presigned POST -> проверить через `HeadObject` -> отметить `UPLOADED`.
- `PENDING` старше 15 минут лениво удаляются при новом запросе загрузки.
- В UI видны только `UPLOADED`; скачивание идёт по краткоживущему presigned URL.
- Удаление Prisma-строки не удаляет байты из S3 автоматически.

### AI-инсайты

- Server Action получает список из БД и проверяет доступ в текущем пространстве.
- Внешний сервис вызывается через `INSIGHTS_SERVICE_URL` с Bearer secret.
- Лимит — 15 запросов на пользователя в сутки по UTC.
- Вопрос ограничен 500 символами.
- В контекст попадает до 50 записей, до 10 заметок записей и до 8000 символов таких заметок.

## Локализация и интерфейс

- Locale prefix обязателен в URL; новый текст получает ключ во всех четырёх `messages/*.json`.
- Стиль минималистичный, с нейтральной чёрно-белой основой и умеренными акцентами.
- Сохраняются мобильная адаптивность, светлая и тёмная темы, доступные подписи.
- Настройки показа авторов, нумерации записей и кнопки прокрутки хранятся в `localStorage`. Там же лежат активная группа и выбранная вкладка — отдельно для каждого пространства.
- Нумерация записей выключена по умолчанию и включается тумблером; порядок хранится независимо от неё.
- Порядок меняется перетаскиванием за ручку и пунктами «Переместить выше/ниже» в меню записи. Пункты меню — доступная с клавиатуры альтернатива, ручка помечена `aria-hidden`.
- Перетаскивание начинается только с ручки (`dragListener={false}` + `useDragControls`): иначе жест конфликтует с кликом по названию и скроллом страницы.
- При активном поиске порядок менять нельзя: пользователь видит подмножество записей, и перемещение перескакивало бы через скрытые.
- Поиск не подменяет массив записей: `ListsContainer` отдаёт список целиком и отдельно ID совпадений, иначе номера считались бы по подмножеству.
- `src/lib/drag-gate.ts` откладывает realtime-обновление на время жеста: `router.refresh()` посреди перетаскивания срывает его.

## Переменные окружения

Секретные значения никогда не записываются в репозиторий.

- БД: `DATABASE_URL`, `DIRECT_URL`;
- Auth.js: `AUTH_SECRET`, `AUTH_GOOGLE_ID`, `AUTH_GOOGLE_SECRET`, при необходимости `AUTH_URL`;
- Pusher: `PUSHER_APP_ID`, `PUSHER_SECRET`, `NEXT_PUBLIC_PUSHER_KEY`, `NEXT_PUBLIC_PUSHER_CLUSTER`;
- S3: `S3_BUCKET_NAME`, `S3_REGION`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`;
- AI: `INSIGHTS_SERVICE_URL`, `INSIGHTS_SERVICE_SECRET`;
- логирование: необязательный `LOG_LEVEL`, по умолчанию `info`.

## Разделение сред

Разработка не имеет доступа к боевым данным. Разведены три сервиса, способные их изменить; для каждого production, Preview на Vercel и локальная среда используют свой ресурс.

- БД — отдельная ветка Neon. Prisma CLI читает корневой `.env`, поэтому боевой URL в нём означал бы, что любая локальная команда Prisma работает с production. Боевые строки подключения существуют только в environment variables Vercel и в GitHub Secrets.
- S3 — отдельный бакет и отдельный IAM-пользователь. Причина: база хранит только ключи, файл существует в одном экземпляре, и на общем бакете удаление вложения в dev-среде стирало боевой файл. Политика dev-пользователя повторяет боевую и ограничена префиксом `lists/*`: расхождение в правах дало бы ключ, работающий локально и падающий в production.
- Pusher — отдельное приложение. Уведомления идут в каналы `private-user-<id>`, а ID пользователей в копии базы совпадают с боевыми, поэтому на общем приложении локальные мутации дёргали вкладки реальных пользователей.
- AI-сервис общий и разделения не требует: суточный лимит считается в `AiInsightUsage`, у каждой базы счётчик свой.

Следствие для пересоздания dev-ветки: приехавшие из прода строки `Attachment` указывают на объекты боевого бакета, которых в dev-бакете нет. Такие вложения локально не открываются, а их удаление обращается к несуществующему ключу и боевой файл не затрагивает.

## Команды и проверка

- `npm run dev` — локальный dev server;
- `npm run lint` — ESLint;
- `npm run build` — production build Next.js без обращения к БД;
- `npm run build:deploy` — `prisma migrate deploy`, затем build; вызывается только хостингом через `buildCommand` в `vercel.json`;
- `npm run migrate:deploy` — применить миграции к текущему `DATABASE_URL` осознанно и вручную;
- `npm start` — запуск production build;
- `npm run postinstall` — генерация Prisma Client.

Отдельного test script сейчас нет.

- 2026-07-22: доступ к спискам переведён со старой связи `sharedWith` на явную модель `ListShare` с ролью и пространством получателя.
- 2026-07-22: завершён контракт пространств — собственные списки, группы и полученные shares рассматриваются в контексте `spaceId`.
- 2026-07-22: добавлены plain-text заметки списков и записей с version-based защитой от потери совместных изменений.
- 2026-07-22: общие инструкции вынесены в `AGENTS.md`, устойчивый контекст — в этот файл; `CLAUDE.md` импортирует общие инструкции.
- 2026-07-24: среда разработки отделена от production по базе, S3 и Pusher — см. «Разделение сред». Одновременно `npm run build` перестал применять миграции: раньше обычная локальная сборка накатывала их на боевую базу, потому что `.env` содержал production-подключение. Теперь миграции при деплое выполняет `build:deploy`, назначенный `buildCommand` в `vercel.json`.
- 2026-07-23: порядок записей стал явным полем `Item.position` типа `Float`. Дробный тип выбран ради одной записи на перемещение и устойчивости к параллельным перемещениям разных записей: перенумерация всего списка стоила бы O(n) записей до удалённой БД и приводила бы к взаимному затиранию.
- 2026-07-23: видимый номер записи решено не хранить. Все продуктовые правила («удалили — последующие −1», «выполнили — потеряла номер») выполняются сами собой, если номер вычисляется при рендере.
- 2026-07-23: перенос записи между списками не потребовал изменений схемы — достаточно смены `listId`. Ограничение «в рамках одного пространства» тоже не потребовало отдельного кода: оба списка ищутся через `listInSpaceWhere` с одним `spaceId`, поэтому список из другого пространства просто не находится.
- 2026-07-23: справочник списков для переноса передаётся контекстом `ListsDirectoryProvider`, а не пропсом. Путь до `SmartList` идёт через `memo`-обёрнутый `ListCard`, и новый массив пропом на каждый рендер сбрасывал бы мемоизацию всех карточек.
- 2026-07-23: оптимистичное отображение переноса намеренно асимметрично. Состояние записей изолировано в `useOptimistic` каждого `SmartList`, поэтому запись сразу пропадает из исходного списка, а в целевом появляется со свежими данными. Симметрия потребовала бы поднять записи в `ListsContainer` — это риск для порядка и нумерации ради одного кадра задержки.
- 2026-07-23: снятие галки возвращает запись на прежнее место, а не в конец списка. Промах по чекбоксу случается чаще осознанного возврата, а `position` при переключении статуса не пишется вовсе.
- 2026-07-23: длинная заметка уходит в диалог по факту переполнения блока, а не по числу символов. Порог в символах непредсказуем для пользователя, не переносится между шириной экрана и ломается при пересечении границы во время набора. Диалог рендерится порталом: у панели заметки есть анимируемый framer-motion предок с `transform`, который стал бы содержащим блоком для `position: fixed`.
