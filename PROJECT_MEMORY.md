**Последнее обновление:** 2026-07-28
**Состояние:** активная разработка

## Назначение

Smart Lists — локализованное веб-приложение для личных и совместных списков. Пользователь организует списки по пространствам и группам, совместно редактирует записи и заметки, прикрепляет файлы и может запрашивать AI-инсайт.

Есть два режима данных:

- авторизованный — PostgreSQL, совместный доступ, Pusher, S3 и AI;
- гостевой — локальные данные браузера без шаринга, realtime, вложений и AI.

## Актуальный стек

- Next.js `16.1.4`, App Router, Server Components и Server Actions;
- React `19.2.3`, TypeScript strict, Tailwind CSS 4, Framer Motion и dnd-kit;
- Auth.js v5 с Google OAuth и Prisma Adapter;
- Prisma `6.19.2` и PostgreSQL;
- `next-intl`: `ru`, `vi`, `en`, `ja`; default locale — `en`;
- Pusher, приватный S3-бакет и внешний FastAPI-сервис AI-инсайтов;
- Zod, Pino, React Hot Toast, `next-themes` и `lucide-react`;
- Vitest — юнит-тесты чистых функций и схем валидации;
- React Markdown — только для ответов AI-инсайтов; остальной пользовательский текст разметку не разбирает;
- Vercel region — `sin1`.

Точные версии всегда смотри в `package.json` и `package-lock.json`.

## Модель данных и права доступа

### Авторизация

- Вход выполняется через Google OAuth.
- Email должен существовать в `AllowedEmail`; whitelist управляется напрямую в БД.
- Сессии хранятся через Prisma Adapter; callback добавляет `session.user.id`.
- При создании пользователя идемпотентно создаётся default-пространство.

### Пространства

- `Space` — верхний уровень организации списков пользователя.
- Default-пространство существует всегда, не удаляется и имеет ID `space_default_<userId>`.
- Допускается до пяти дополнительных пространств; их нормализованные имена уникальны для пользователя.
- Текущее пространство находится в URL `/{locale}/spaces/{spaceId}`; последнее выбранное хранится в httpOnly cookie `smart-lists-space`.
- Удаление дополнительного пространства удаляет его списки и группы, убирает размещённые там чужие списки и запускает фоновую очистку S3.

### Списки и совместный доступ

- `List` принадлежит одному владельцу и одному его пространству.
- `ListShare` даёт роль `EDITOR` и размещает список в пространстве получателя.
- Ключ `ListShare(listId, userId)` означает одно размещение списка на получателя.
- Видимость определяет `listInSpaceWhere(userId, spaceId)`: собственный список в пространстве либо share, размещённый в нём.
- Редактор изменяет содержимое. Управление владением, удалением списка и участниками остаётся за владельцем.
- `ListGroup` — личная организация внутри пространства. Список может находиться в разных группах у разных пользователей.

### Записи и заметки

- `Item` принадлежит списку и может хранить автора добавления.
- Список и запись имеют plain-text заметку до 4000 символов. Разметка не разбирается: текст показывается как есть, переносы строк сохраняются.
- `noteVersion` обеспечивает optimistic concurrency; конфликт возвращает актуальную заметку и версию.
- Поиск учитывает названия и заметки, UI показывает фрагмент совпадения.
- Заметка сохраняется только явным действием: кнопкой или Ctrl/Cmd+Enter в textarea. Одиночный Enter переносит строку. Хоткей полностью эквивалентен кнопке — та же ожидаемая версия и то же условие активности, поэтому перезапись чужой правки остаётся отдельным действием.
- Заметка читается в карточке, но по высоте обрезается; полный текст и редактор открываются в диалоге. Признак — фактическое переполнение блока, а не длина текста: одна и та же заметка на узком экране занимает втрое больше строк. Черновик общий для встроенного редактора и диалога, поэтому переключение между ними не теряет набранное.
- Запись можно перенести или скопировать в другой список того же пространства. Перенос меняет `listId` у существующей строки, копия создаётся заново: `noteVersion` обнуляется, отметка о выполнении сбрасывается, автором становится копирующий. В обоих случаях запись встаёт в конец списка-получателя.

### Порядок записей

- Порядок задаёт `Item.position` типа `Float`. Значимо только сравнение позиций между собой.
- Выборка сортируется по `position`, затем `createdAt` и `id`: тайбрейк делает порядок детерминированным при равных позициях.
- Порядок общий для всех участников списка. Персонального порядка нет.
- Новая запись получает `максимум + 1`. Максимум читается тем же запросом, что и проверка доступа.
- Перемещение выполняет `moveItem`: клиент присылает ID новых соседей, сервер читает их позиции из БД и пишет середину — одну строку. Целевой индекс не используется: он устаревает при параллельных изменениях.
- Если середина не легла строго между соседями, список перенумеровывается целиком в транзакции. Ветка вырожденная и пишет отдельное сообщение в лог.
- Пропавший сосед возвращает `stale` без записи в БД; клиент откатывает оптимистичное перемещение.
- Отметка о выполнении и снятие отметки `position` не меняют. Выполненная запись выпадает из нумерации и уходит в нижний блок, снятие галки возвращает её на своё место.
- Видимый номер нигде не хранится: это индекс среди невыполненных записей, вычисляемый при рендере. Поэтому удаление и выполнение не требуют перенумерации.
- Гостевой режим порядок хранит порядком массива в `localStorage`; поля `position` там нет. Контракт с UI общий: массив записей всегда приходит упорядоченным.

### Порядок групп

- Личный порядок групп задаёт `ListGroup.position` типа `Float` внутри пары `userId + spaceId`; вкладка «Все» виртуальная и в БД не хранится.
- Новая группа получает `максимум + 1`. Выборки групп сортируются по `position`, затем `createdAt` и `id`; тот же массив используется вкладками, меню назначения списка, бейджами и диалогом переноса записи.
- `moveGroup` принимает ID новых соседей и проверяет группу, пространство и актуальность разрыва по БД. Обычно обновляется одна позиция; при исчерпании точности все группы пространства перенумеровываются в транзакции.
- UI использует dnd-kit с собственной стратегией многострочной раскладки: она пересчитывает flex-позиции с исходными ширинами вкладок и применяет только translate, поэтому вкладки разной ширины не деформируют текст и не перекрывают соседей. Ручка показывается только у активной группы, Keyboard Sensor даёт эквивалентное перемещение с клавиатуры, а при наведении на ручку и во время переноса вкладка в тёмной теме получает тёмный контрастный фон для видимости системного курсора. «Все» находится вне `SortableContext` и не перемещается.
- Гость хранит порядок самим массивом `groups` в `localStorage`; интерфейс и контракт `ListsApi` у обоих режимов одинаковы.

### Порядок списков в группах

- Порядок списка персонален и принадлежит его членству в конкретной группе, а не самому `List`: явная модель `ListGroupMembership` хранит `listId + groupId + position` и отображается на прежнюю таблицу `_ListGroupMembers`.
- Один список может состоять в нескольких группах с независимым порядком. Вкладка «Все» отдельного порядка не хранит и показывает доступные списки по `createdAt desc`, затем `id`.
- `moveListInGroup` использует тот же контракт соседей и midpoint/rebalance, что порядок записей и групп: сервер проверяет пользователя, пространство, доступность списка, членство и актуальность разрыва. Это личная организация, поэтому после ревалидации Pusher не отправляется.
- Добавление существующего списка в группу идемпотентно и ставит его в конец. Перетаскивание на другую вкладку именно добавляет членство, сохраняя исходную группу; если членство уже есть, действие ничего не меняет. Новый список, созданный при активной группе, появляется в её начале.
- DnD работает с единым плоским порядком до `splitIntoColumns`: колонки остаются только представлением и никогда не сохраняются. Поэтому перенос между колонками меняет тот же логический массив, что пункты «Переместить выше/ниже» в меню.
- Во вкладке «Все» ручки списков скрыты: глобальный порядок там не меняется, а ручка создавала ложное ожидание перестановки. Перетаскивание на другую вкладку группы доступно из конкретной активной группы; исходное членство сохраняется. Во время поиска DnD списков отключён, потому что видимое подмножество не задаёт однозначных соседей; после drop активная группа не переключается.
- За курсором движется компактный overlay. Исходная раскрытая карточка во время жеста полностью прозрачна: её полноразмерная проекция перекрывала соседей и мешала читать целевое место. Для свёрнутой карточки лёгкая проекция остаётся полезной и сохраняется. При переходе между колонками exit-копия карточки анимируется через `AnimatePresence mode="popLayout"`: она остаётся видимой на прежнем месте, но сразу исключается из flex-раскладки и не сдвигает остальные списки.
- Пока Server Action сохраняет новый порядок, повторный жест заблокирован, но ручки не удаляются из DOM, а остаются видимыми disabled. Это сохраняет геометрию заголовков без риска отправить параллельные перемещения с устаревшими соседями.
- Гость хранит независимый порядок в `group.listIds`. Старые данные только с `list.groupIds` мигрируют при чтении, сохраняя прежний глобальный порядок; устаревшие и повторные ID очищаются.

## Ключевые потоки

### Данные и realtime

- `ListsDataFetcher` параллельно загружает списки и личные группы точечными `select`.
- Клиентский UI работает через `ListsApi`; серверный провайдер добавляет `spaceId` и Pusher `socketId`.
- После мутации layout-level `revalidatePath` возвращает вкладке-автору свежий RSC payload.
- Клиент подписывается на `private-user-<userId>`; endpoint `/api/pusher/auth` разрешает только собственный канал.
- Событие `refresh` вызывает `router.refresh()`; вкладка-автор исключается по `socketId`.
- Ошибка Pusher логируется и не отменяет успешную запись в БД.
- Мутация, затрагивающая два списка сразу, уведомляет участников обоих через `notifyListsMembers`: наборы получателей у списков разные, а объединение в один Set не даёт задвоенный `refresh` тем, кто состоит в обоих.

### Гостевой режим

- Включается только при `AppSetting` с ключом `guestModeEnabled` и значением `true`.
- httpOnly cookie `guest-mode` выбирает гостевой UI, данные находятся в `localStorage`.
- Отключение режима в БД или выход гостя не удаляет локальные данные.
- Гостю недоступны пространства, шаринг, Pusher, AI и вложения.
- Гостевая реализация `ListsApi` повторяет поддерживаемые базовые операции без обращения к БД.

### Вложения

- Разрешены PNG, JPEG, TXT и PDF до 10 MiB.
- Лимиты: 5 файлов на список и 20 файлов на загрузившего пользователя.
- Поток: создать `PENDING` -> загрузить напрямую по presigned POST -> проверить через `HeadObject` -> отметить `UPLOADED`.
- `PENDING` старше 15 минут лениво удаляются при новом запросе загрузки.
- В UI видны только `UPLOADED`; скачивание идёт по краткоживущему presigned URL.
- Удаление Prisma-строки не удаляет байты из S3 автоматически.

### AI-инсайты

- Server Action получает список из БД и проверяет доступ в текущем пространстве.
- Внешний сервис вызывается через `INSIGHTS_SERVICE_URL` с Bearer secret.
- Лимит — 15 запросов на пользователя в сутки по UTC.
- Вопрос ограничен 500 символами.
- В контекст попадает до 50 записей, до 10 заметок записей и до 8000 символов таких заметок.

## Локализация и интерфейс

- Locale prefix обязателен в URL; новый текст получает ключ во всех четырёх `messages/*.json`.
- Стиль минималистичный, с нейтральной чёрно-белой основой и умеренными акцентами.
- Сохраняются мобильная адаптивность, светлая и тёмная темы, доступные подписи.
- Настройки показа авторов, нумерации записей, счётчика выполненных и кнопки прокрутки хранятся в `localStorage`. Там же лежат активная группа — отдельным ключом на пространство (`activeGroupId:<spaceId>`) — и выбранная вкладка, общая для всех пространств (`activeTab`). У гостя свои ключи с префиксом `guest:`.
- В шапке карточки стоит счётчик «выполнено / всего». Он показывает прогресс, а не остаток: `N / M` в списке задач читается именно так, и обратный счёт сбивал бы с толку — отметка записи уменьшала бы первое число. Счётчик включён по умолчанию и выключается тумблером в настройках; тумблер один на раскрытые и свёрнутые карточки. У пустого списка счётчика нет.
- Заметка списка стоит выше скрываемого тела и потому доступна у свёрнутой карточки: она относится к списку целиком, как заголовок, а не к его содержимому. Полный текст открывается диалогом изнутри `NotePanel`; если бы блок лежал в теле, диалог унаследовал бы `visibility: hidden`. Сворачивание заметку закрывает — иначе свёрнутая карточка осталась бы высокой и это читалось бы как сбой. Пустую заметку по-прежнему создают из меню, поэтому кнопка в шапке появляется только когда текст есть.
- Карточку списка можно свернуть до шапки: остаются заголовок, счётчик и меню действий. Место счётчика от свёрнутости не зависит, поэтому при сворачивании он не прыгает.
- Сворачивание анимировано высотой (0.18s; при `prefers-reduced-motion` и на тач-устройствах — мгновенно). Анимация высоты заставляет браузер пересчитывать раскладку каждый кадр, и на телефоне этого бюджета не хватает: переход виден как рывок, а мгновенное сворачивание там выглядит лучше плохой анимации. Тело остаётся смонтированным, поэтому свёрнутая карточка получает `inert` и `visibility: hidden`: нулевая высота с обрезкой прячет содержимое только визуально, оставляя его в фокусе и в поиске по странице. `visibility` снимается на время анимации — иначе сворачивать было бы нечего. Обрезка тоже включается только на время анимации и в свёрнутом виде: у раскрытой карточки она срезала бы меню записи, выходящее за нижний край короткого списка.
- `overflow` и `visibility` тела переключаются прямой записью в DOM из колбэков анимации, а не через состояние React. Через состояние это стоило вчетверо: `setState` на старте анимации перерисовывал тело карточки вместе со `SmartList`, и первый кадр растягивался с 22 до 91 мс — клик, пауза, рывок. Ни одно из этих свойств на разметку React не влияет, поэтому ререндер там не нужен. Мемоизация `SmartList` как альтернатива проверялась замером и выигрыша не дала.
- Карточки разложены по трём колонкам вручную (`splitIntoColumns`), а не средствами `columns` или грида. Обе автоматические раскладки конфликтуют со сворачиванием: в multicol колонка карточки вычисляется из высот, поэтому изменение высоты перебрасывало соседей между колонками прямо посреди анимации; в гриде ряды выровнены по горизонтали, поэтому рядом со свёрнутой карточкой оставалась пустота во всю высоту раскрытой соседки. Здесь колонка задана порядковым номером и от высот не зависит вовсе.
- Разметка всегда содержит три куска, и оба крайних случая CSS собирает сам: ниже `xl` обёртки колонок получают `display: contents`, выпадают из раскладки, и карточки выстраиваются одним потоком в порядке DOM. Поэтому серверная разметка сразу верна и на телефоне, и на десктопе.
- Две колонки на среднем экране — единственный случай, который CSS собрать не может: из трёх кусков две колонки не склеить. Он включается после гидрации подпиской на медиа-запрос `MEDIUM_SCREEN_QUERY` через `useSyncExternalStore` (серверный снимок — всегда `false`). Это единственное место, где брейкпоинт продублирован в коде; значения в `rem`, как у Tailwind 4, иначе они разъедутся при нестандартном размере шрифта.
- Контейнер колонок имеет `key` по их числу. Без него при смене числа колонок карточка на мгновение оказывалась в DOM дважды: старая копия доигрывала исчезновение в прежней колонке, пока новая появлялась в соседней. Ключ размонтирует старое дерево мгновенно — `AnimatePresence` не анимирует собственное исчезновение.
- Раскладка идёт подряд идущими кусками, а не по остатку от деления: сохраняется порядок чтения сверху вниз по колонке, и соседи по вертикали остаются соседями по номеру — это понадобится, когда карточки можно будет перетаскивать. Следствие независимости от высот: колонки заканчиваются на разной высоте. Это персональная настройка отображения на устройство — набор ID лежит в `localStorage` ключом на пространство (`collapsedLists:<spaceId>`), в БД её нет и другим участникам расшаренного списка она не видна. ID исчезнувших списков отсеиваются при чтении, иначе набор рос бы вечно.
- Меню действий списка раскрывается вверх, когда снизу не хватает места, — но только если вверху оно действительно помещается: у карточки на коротком экране может не хватать места с обеих сторон, и переворот увёл бы меню за верхнюю границу окна. Высота меню известна лишь после отрисовки, поэтому решение принимает layout-эффект — до того, как браузер нарисует кадр.
- Меню действий списка позиционируется `fixed` по координатам своей кнопки, а не `absolute`. Причина в `columns`-раскладке: Chrome учитывает высоту абсолютно спозиционированного потомка при балансировке колонок, и меню, вылезающее за нижний край карточки, выталкивает соседей в другую колонку. У развёрнутой карточки меню умещалось в её высоту, у свёрнутой раскладка распадалась. Меню записи и меню групп за нижний край не выходят, их это не касается.
- При активном поиске свёрнутость игнорируется, а сохранённое состояние не меняется: карточка отрисована, только если совпадение в ней есть, и оставить её закрытой значило бы показать результат, на который нельзя посмотреть.
- Нумерация записей выключена по умолчанию и включается тумблером; порядок хранится независимо от неё.
- Порядок меняется перетаскиванием за ручку и пунктами «Переместить выше/ниже» в меню записи. Пункты меню — доступная с клавиатуры альтернатива, ручка помечена `aria-hidden`.
- Перетаскивание начинается только с ручки (`dragListener={false}` + `useDragControls`): иначе жест конфликтует с кликом по названию и скроллом страницы.
- При активном поиске порядок менять нельзя: пользователь видит подмножество записей, и перемещение перескакивало бы через скрытые.
- Поиск не подменяет массив записей: `ListsContainer` отдаёт список целиком и отдельно ID совпадений, иначе номера считались бы по подмножеству.
- `src/lib/drag-gate.ts` откладывает realtime-обновление на время жеста: `router.refresh()` посреди перетаскивания срывает его.
- Тот же затвор используется при перетаскивании групп: несвязанный realtime-refresh не должен размонтировать двумерный DnD-жест.

## Переменные окружения

Секретные значения никогда не записываются в репозиторий.

- БД: `DATABASE_URL`, `DIRECT_URL`;
- Auth.js: `AUTH_SECRET`, `AUTH_GOOGLE_ID`, `AUTH_GOOGLE_SECRET`, при необходимости `AUTH_URL`;
- Pusher: `PUSHER_APP_ID`, `PUSHER_SECRET`, `NEXT_PUBLIC_PUSHER_KEY`, `NEXT_PUBLIC_PUSHER_CLUSTER`;
- S3: `S3_BUCKET_NAME`, `S3_REGION`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`;
- AI: `INSIGHTS_SERVICE_URL`, `INSIGHTS_SERVICE_SECRET`;
- логирование: необязательный `LOG_LEVEL`, по умолчанию `info`.

## Разделение сред

Разработка не имеет доступа к боевым данным. Разведены три сервиса, способные их изменить; для каждого production, Preview на Vercel и локальная среда используют свой ресурс.

- БД — отдельная ветка Neon. Prisma CLI читает корневой `.env`, поэтому боевой URL в нём означал бы, что любая локальная команда Prisma работает с production. Боевые строки подключения существуют только в environment variables Vercel и в GitHub Secrets.
- S3 — отдельный бакет и отдельный IAM-пользователь. Причина: база хранит только ключи, файл существует в одном экземпляре, и на общем бакете удаление вложения в dev-среде стирало боевой файл. Политика dev-пользователя повторяет боевую и ограничена префиксом `lists/*`: расхождение в правах дало бы ключ, работающий локально и падающий в production.
- Pusher — отдельное приложение. Уведомления идут в каналы `private-user-<id>`, а ID пользователей в копии базы совпадают с боевыми, поэтому на общем приложении локальные мутации дёргали вкладки реальных пользователей.
- AI-сервис общий и разделения не требует: суточный лимит считается в `AiInsightUsage`, у каждой базы счётчик свой.

Следствие для пересоздания dev-ветки: приехавшие из прода строки `Attachment` указывают на объекты боевого бакета, которых в dev-бакете нет. Такие вложения локально не открываются, а их удаление обращается к несуществующему ключу и боевой файл не затрагивает.

### Тесты

Юнит-тесты лежат рядом с проверяемым модулем (`*.test.ts`), общие — в `test/`.
Прогон не поднимает Next.js и не обращается к PostgreSQL, S3 и Pusher, поэтому
не требует ни секретов, ни сети.

Покрыто: Zod-схемы, фильтр видимости `listInSpaceWhere`, хелперы заметок и
вложений, затвор перетаскивания, раскладка карточек по колонкам, набор
свёрнутых карточек (разбор недоверенного
значения из localStorage и уборка ID), генерация ID, а также гостевая реализация
`ListsApi` целиком — порядок записей и списков в независимых группах,
назначение с сохранением исходной группы, перенос и копирование между списками,
версионирование заметок и поведение при отказе localStorage. Отдельно
проверяется согласованность `messages/*.json`: наборы ключей всех четырёх
локалей совпадают, а перевод не вводит ICU-аргументов, которых нет в `ru`.
Обратное допустимо — во вьетнамском и японском нет числовых форм, поэтому
`{count}` там осознанно не используется.

Конфигурация — `vitest.config.ts`. Алиас `@/` повторяет tsconfig; пакет
`server-only` подменяется заглушкой `test/stubs/server-only.ts`, иначе модули с
`import "server-only"` не выполняются вне RSC-контекста. Модули, создающие
PrismaClient на импорте, мокаются через `vi.mock("@/lib/db", …)`. localStorage
заменяет `test/memory-storage.ts` — гостевому коду нужен только Storage, и
поднимать ради него jsdom незачем.

### Интеграционные тесты

Server Actions проверяются против настоящего PostgreSQL — это единственный
способ покрыть права доступа, привязку к пространству, каскады и concurrency.
Файлы — `test/integration/*.int.test.ts`, конфиг — `vitest.integration.config.ts`
(отдельный от юнитов: те быстрые и без зависимостей, эти требуют базы).

БД поднимается в Docker (`docker-compose.test.yml`, порт 5433, данные в tmpfs).
`test/integration/global-setup.ts` ждёт готовности и накатывает миграции тем же
`prisma migrate deploy`; перед этим — защита: миграции применяются, только если
имя базы содержит `test` (обход — `ALLOW_NON_TEST_DB=1`). Между тестами
`beforeEach` делает `TRUNCATE ... CASCADE`, поэтому файлы гоняются
последовательно (`fileParallelism: false`). Внешние сервисы замоканы в
`test/integration/setup.ts`: сессия управляется через `setSessionUser`, `after`
копит колбэки и запускается вручную через `flushAfter` (Pusher/S3-побочки
проверяются как факт), Pusher и сетевые функции S3 — no-op со шпионами, а
чистый `buildAttachmentKey` оставлен настоящим. Фикстуры — `factories.ts`.

Покрыто: контроль доступа (владелец vs редактор), изоляция пространств,
жизненный цикл шаринга, CRUD пространств (лимит, каскад, защита default),
порядок записей `moveItem`, списков `moveListInGroup` и групп `moveGroup`,
включая независимость групп, проверку устаревших соседей и ветку
перенумерации, перенос и копирование между списками,
concurrency заметок по `noteVersion`, группы и вложения
(two-phase-загрузка, квоты на список и пользователя, ленивая уборка PENDING).

### E2E-тесты

Playwright гоняет настоящий браузер против production-сборки приложения
(`next build && next start`, порт 3100) и отдельной базы в Docker
(`docker-compose.test.yml`, профиль `e2e`, порт 5434). Файлы —
`test/e2e/*.e2e.ts`, конфиг — `playwright.config.ts`.

Вход через Google не выполняется: тест создаёт строку `Session` — ту же, что
пишет Prisma Adapter при настоящем входе, — и кладёт её токен в cookie
`authjs.session-token`. Приложение такую сессию не отличает от полученной по
OAuth. Следствие: колбэк `signIn` и whitelist `AllowedEmail` E2E не покрывает.

Изоляция держится на данных, а не на очистке: каждый тест работает под
собственным пользователем со своим пространством, поэтому файлы идут
параллельно. `TRUNCATE` выполняется один раз в `global-setup.ts` — посреди
прогона он снёс бы данные соседнего теста. Из этого следует правило для новых
проверок: любой запрос к БД в ассерте фильтруется по своим `listId`/`userId`;
`count()` по всей таблице поймает чужие строки. Единственное общее состояние —
`AppSetting` гостевого режима, поэтому `guest.e2e.ts` объявлен serial.

Селекторы — `data-testid`. Текст в них не годится: интерфейс переводится на
четыре языка, и тест ломался бы при правке перевода. Дополнительный слой —
хелпер `visible()`: на время переходов и анимаций в DOM остаётся скрытая копия
поддерева, и strict mode Playwright считает её вторым совпадением.

#### Зависший E2E-сервер на Windows

На Windows Playwright иногда завершает тесты, но не останавливает дочерний
`next start`: команда висит после строки `N passed`, а порт `3100` остаётся
занят. Раньше локальный `reuseExistingServer` молча подключал следующий прогон
к этому процессу, поэтому свежие тесты могли проверять предыдущую `.next`-
сборку. Теперь переиспользование по умолчанию выключено и включается только
явно через `E2E_REUSE_SERVER=1`.

Если E2E завис после успешного результата или сообщает занятый порт:

1. Найти слушающий PID: `netstat -ano | findstr :3100`.
2. Проверить команду процесса:
   `Get-CimInstance Win32_Process -Filter "ProcessId = <PID>" | Select-Object ProcessId, ParentProcessId, CommandLine`.
3. Только если `CommandLine` указывает на `smart-lists` и `next start`, остановить
   именно этот PID: `Stop-Process -Id <PID> -Force`.
4. Повторить прогон. `E2E_SKIP_BUILD=1` использовать только после успешного
   `npm run build`; иначе Playwright намеренно запустит имеющуюся старую сборку.

Если в выводе уже есть `N passed`, зависла лишь уборка web-server, а не сами
тесты. В CI проблема не наблюдалась: там существующий сервер никогда не
переиспользуется, а процесс живёт внутри одноразового Linux-раннера.

Покрыто: гейты и редиректы (локаль, чужое и несуществующее пространство, cookie
последнего пространства), жизненный цикл списка и записи с проверкой после
перезагрузки, порядок записей перетаскиванием и пунктами меню, запрет
перетаскивания за название и при активном поиске, заметки (сохранение, переход
в диалог по переполнению, общий черновик, конфликт версий, Ctrl+Enter против
одиночного Enter), поиск по названиям,
записям и заметкам, сворачивание карточки с памятью после перезагрузки, его
стык с поиском, неизменность колонок при сворачивании, число колонок на трёх
ширинах экрана, устойчивость раскладки при открытом меню и переворот меню у
нижнего края окна, доступность заметки у свёрнутой карточки, счётчик
выполненных и его тумблер, многострочное перетаскивание групп, соответствие
порядка в меню назначения и память активной группы по пространству,
перетаскивание карточек между колонками с сохранением после перезагрузки,
назначение списка drop-ом на вкладку с сохранением исходной группы и
клавиатурная альтернатива через меню, CRUD
пространств с лимитом, шаринг в двух браузерных контекстах (редактор не видит
операций владельца) и гостевой режим целиком.

Не покрыто намеренно: OAuth-хендшейк Google, realtime через Pusher, вложения
(нужен S3-совместимый сервис) и AI-инсайты (нужен внешний сервис).

### CI

`.github/workflows/ci.yml` на каждый push и pull request запускает две job.
`checks` — lint, typecheck, юнит-тесты и `npm run build` с заведомо нерабочими
`DATABASE_URL`, `AUTH_SECRET`, `NEXT_PUBLIC_PUSHER_*` (сборка в БД не ходит).
`integration` — интеграционные тесты против service-контейнера `postgres:17`;
`prisma migrate deploy` там применяется только к эфемерной базе раннера.
`e2e` — Playwright с Chromium против такого же service-контейнера на порту 5434;
при падении отчёт со скриншотами и видео выгружается артефактом.
Боевые ресурсы не затрагиваются ни одной job; миграции против прод-базы
применяет лишь `build:deploy`, назначенный `buildCommand` в `vercel.json`.

Установка в CI — `npm ci`, поэтому `package-lock.json` обязан быть источником
истины для Linux. Разработка идёт на Windows, но `npm install` там записывает в
lock только Windows-специфичные платформенные пакеты и опускает вложенные
optional-зависимости Linux-вариантов (`@emnapi/*` у wasm-фолбэков). С таким
lock `npm ci` на раннере падает с «Missing … from lock file».

Чинить нужно на Linux, но не регенерацией с нуля: `rm package-lock.json`
поднимает все плавающие (`^`) зависимости до свежих версий и меняет поведение
инструментов (так `eslint-plugin-react-hooks` прыгнул 7.0.1 → 7.1.1 и
завалил lint новым правилом). Правильный рецепт — в Linux-контейнере
(`node:24`, как в CI и в сборке Vercel) выполнить обычный `npm install` поверх
существующего lock: он уважает уже закреплённые резолюции и лишь дописывает
недостающее. Затем проверить, что `npm ci --ignore-scripts` там проходит.
Устанавливать в контейнере нужно в его собственную ФС, а не в смонтированный
Windows-том: bind-mount в Docker Desktop пишет тысячи файлов мучительно долго.

### Бэкап базы

`.github/workflows/backup.yml` ежедневно снимает `pg_dump -Fc` и кладёт его в
отдельный приватный S3-бакет в `ap-northeast-1` под ключом
`backups/smart-lists-<дата JST>.dump`. Расписание — `0 15 * * *`, то есть
полночь по Токио; GitHub запускает cron с задержкой до полутора часов.

Дамп содержит email пользователей, OAuth-токены `Account` и всё содержимое
списков, поэтому артефакты Actions для него не годятся: их может скачать любой,
у кого есть доступ на чтение репозитория, а репозиторий планируется публиковать.
Бакет заведён отдельно от бакета вложений, чтобы ключи в GitHub давали право
только на запись бэкапов и не открывали доступ к файлам пользователей.

Доступ к AWS выдаётся через OIDC, долгоживущих ключей в репозитории нет.
GitHub подписывает id-токен, роль `smart-lists-backup-ci` меняет его на временные
креды и разрешает единственное действие — `s3:PutObject` в `backups/*`. Trust
policy сверяет `sub` с `repo:kzhirikhin/smart-lists:ref:refs/heads/main`, поэтому
форки и pull request'ы кредов не получают. Обратная сторона: переименование
репозитория, смена владельца или ветки по умолчанию ломает обмен с `AccessDenied`
— тогда нужно править условие в trust policy роли.

Секреты репозитория: `BACKUP_S3_BUCKET`, `BACKUP_AWS_ROLE_ARN` (плюс уже
существовавший `DATABASE_URL`). Срок хранения задаётся lifecycle-правилом бакета
`expire-backups-30d`, а не workflow.

## Важные решения

- 2026-07-26: неявная many-to-many связь списков и групп стала явной `ListGroupMembership` с `Float position`. Позиция находится на членстве, потому что один и тот же список может иметь разный личный порядок в нескольких группах; глобальный `List.position` сделал бы эти порядки взаимозависимыми. Таблица сохранена как `_ListGroupMembers`, поэтому миграция добавляет позицию без переноса связей. DnD работает над плоским порядком до разбиения на колонки, а drop на вкладку добавляет целевую группу и намеренно сохраняет исходную.
- 2026-07-25: заведены E2E-тесты Playwright (49 проверок) и третья CI-job. Покрытие выбрано по принципу «только то, чего не видят юниты и интеграционные»: связка Action → `revalidatePath` → RSC payload → `useOptimistic`, состояние в `localStorage` и cookie, порталы и блокировка фона, жест перетаскивания, условный рендер по роли и локализованные редиректы. Сессия подставляется строкой `Session` в базе, а не OAuth: внешний вход требует секретов, уводит на чужой домен и ломается при смене верстки провайдера. Изоляция сделана данными (свой пользователь на тест), а не очисткой базы: приложение работает с той же базой параллельно, и `TRUNCATE` посреди прогона снёс бы данные соседнего теста.

Выбор БД-в-контейнере, а не транзакции-с-откатом: сами Actions используют `$transaction`, и вложенный откат хрупок — `TRUNCATE` между тестами надёжнее. Сессия, Pusher, S3 и ревалидация Next замоканы, база настоящая. Покрытие идёт по продуктовым правилам доступа и concurrency, а не по строкам: именно проверки владельца/редактора и привязки к `spaceId` ломаются тихо, без падения сборки.
- 2026-07-24: заведены юнит-тесты и CI. Тесты умышленно ограничены кодом, не требующим БД и секретов: прогон одинаково работает локально и в CI, а падение теста означает изменение поведения, а не сломанное окружение. Написание тестов нашло два реальных дефекта:
  - `isAllowedType` проверял MIME-тип оператором `in` и потому пропускал `constructor` и `toString` из прототипа `Object`; дальше по потоку загрузки `getCategory` возвращал для такого типа `null`, приведённый `as FileCategory`. От записи в БД спасало только то, что следом `buildAttachmentKey` возвращал `null`. Заменено на `Object.hasOwn`.
  - `loadGuestData` возвращал ссылку на общую константу `EMPTY_DATA`, когда localStorage пуст, а мутации в гостевом API идут прямо в результат. Списки накапливались в константе на весь срок жизни вкладки: при отказе записи (приватный режим, исчерпанная квота) пользователь получал ошибку, но список оставался в памяти и всплывал при следующем чтении как несуществующий. Пустое состояние теперь создаётся заново на каждый вызов.
